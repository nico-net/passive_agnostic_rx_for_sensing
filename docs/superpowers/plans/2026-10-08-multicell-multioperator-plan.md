# Multi-PCI and multi-operator sensing: ordered work plan

2026-10-08, revised for the 400 MHz final target. **Plan only; no implementation or radio run in this worktree.** **Milestone 1 remains** X410 4 RX, FPGA DDC `2×A+2×B` at about 122.88 MS/s, one process with `CarrierContext × CellContext`, event-driven tracking and shared workers. Its G12/G13/G14 acceptance requires two co-channel PCIs, two simultaneous carriers and two operators with two calibrated antennas per carrier. **Final architecture** is CG_400 four RX each covering about 400 MHz at an actual sample rate near 491.52 MS/s, preferably two QSFP28 100GbE links, GPU channelizer, and every covered carrier on all four antennas. It is enabled only after final gates F1–F8 below. The sequence starts with cheap evidence tests, but production integration waits until the single-cell T26c PDCCH/PDSCH efficiency work, RXR recovery/direct-ring validation, and G10/G11 tracking foundation have passed their own gates. Use the [design](../specs/2026-10-08-multicell-multioperator-design.md) and `PROJECT_MEMORY.md` §§12,14,17–20. Every result names host, capture/cell, RF profile, antennas, commit and evidence label; replay is never called OTA real time.

## Integration order and branch boundaries

The experiments in WP0–WP2 are read-only or isolated diagnostics and may start now. Production packages WP3–WP10 begin **after** the single-cell efficiency changes (T26b/T26c GPU PDCCH FEP, batched PDSCH, known-RNTI scan, queue admission), their live-rate OTA gate, and RXR's timed recovery have landed on the integration base. **Finish and accept WP10 (2+2) before enabling any 400 MHz production path.** WP11–WP16 build the final profile behind separate default-off flags; F1–F8 are additional gates, not replacements for G12–G14. G10/G11 persistence/epoch behavior must be established before G12–G14 acceptance. Rebase once at that point; do not edit T26c's `nr_pdcch_blind_monitor_rt.c`, `nr_pdsch_passive_queue.c`, GPU FEP modules, or the DL/UL branches' solver/UL implementation while those branches are active. Use new context/adapter files and narrow API additions in WP3–WP5; move state owner by owner after those merges. DL and UL owners review the matching context-key and job-tag changes; merge DL and UL first, then this series, one package at a time. Preserve the `nr_csirs_disc.h` contract unless separately approved by its owner.

All new runtime behavior gets its own `ISAC_MCELL_*` flags, default off; the unflagged one-cell path must remain behaviorally identical. Stage only explicit paths, run the frozen sens6 diff gate before each commit, commit on the implementation branch, never push from this plan. Builds/ctest use the shared measurement lock, `nice -n 19`, `-j8`/`-j4`; benchmark, rfsim and GPU throughput use the exclusive lock on an idle host. The orchestrator owns replay and X410 OTA execution. No gNB config/log is receiver input.

## Acceptance detail and stop rules

### Final-profile F1–F8 gates and exact deferred commands

These commands are **prescriptions for the operator after the corresponding WP exists**; none was executed for this document revision. `benchmark_rate --help` and `uhd_usrp_probe --help` were checked locally under `/usr/local`; `mcell_*` programs and `score_gate.py` are **proposed WP11–WP16 deliverables**, not current executables. Their named options and JSON outputs form the acceptance interface that those packages must implement. Replace the `sfp1` IP only after the probe/network preflight establishes the unit's actual address; the values below are the documented CG_400 defaults and current site `sfp0`/management addresses. Configure both host NICs (including DPDK's second-port `dpdk_ipv4` and lcores) before F1; `mgmt_addr` stays on the independent control link. The UHD [X4x0 device arguments/benchmarks and X410 master-clock section](https://files.ettus.com/manual/page_usrp_x4xx.html) document `second_addr`, the one-/two-port RX results, and CG_400's 491.52/500 MHz MCR choices; this target fixes MCR at the **vendor-tested 491.52 MHz**. The [UHD DPDK guide](https://files.ettus.com/manual/page_dpdk.html) requires explicit `mgmt_addr`, `addr`, `second_addr` when DPDK is used. No documented source here fixes the **per-channel link mapping**; F1 measures it. Benchmarks with `--multi_streamer` match UHD's vendor test topology; F2 also runs the production-like **single four-channel streamer**, since the former cannot certify the latter.

```bash
X410_TWO='type=x4xx,addr=192.168.10.2,second_addr=192.168.20.2,mgmt_addr=192.168.30.2,master_clock_rate=491520000,use_dpdk=1,dpdk_num_mbufs=65536'
X410_ONE='type=x4xx,addr=192.168.10.2,mgmt_addr=192.168.30.2,master_clock_rate=491520000,use_dpdk=1,dpdk_num_mbufs=65536'
X410_TWO_KERNEL='type=x4xx,addr=192.168.10.2,second_addr=192.168.20.2,mgmt_addr=192.168.30.2,master_clock_rate=491520000'
```
