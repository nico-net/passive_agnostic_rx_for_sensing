# GPUSHARE — PDSCH GPU work vs CSI-RS discovery on the GB10 (2026-10-11)

Branch `csd/gpu-share` (worktree `rr-csd-gsh`, base `csd/otatest` 7f2a20f2db). Host: DGX Spark GB10 (sm_121, 48 SMs,
CUDA 13.0, driver 580.178.04, unified memory). Every build, test and replay ran through `heavy.sh`; no radio, OTA,
capture or UHD tool. All replay numbers: `tests/passive_rx/timacq_replay.sh`, **SPEED=1**, env
`rr-orchestration/ota/t26r.env` (single line) + `ISAC_PDTIM_PCT=1` already in it, plus the arm's flags.
Commits: 6f13062d4b (build fix), 41f1196135 (SM partition), a11383e94b (GPU LDPC / demod latency).

## Verdict

* **Goal (per-grant decode-time mean < 0.5 ms): not met.** `[MEASURED, DGX GB10 replay]`
  - capture b (Vodafone, 2 runs per arm): sum of PDTIM stage means **842-888 us -> 603-741 us** (final binary, arms F
    and FC below; best earlier arm GI8P0 643/664), per-decode p99 **6.8-7.8 ms -> 2.2-4.6 ms**, p50 465-485 -> 415-445 us;
  - capture 8 (Vodafone 20261008): the run means are set by one 30-140 ms stall per run (1,800-3,200 decodes);
    second-half means 617-667 (A) -> 514-550 us (F);
  - TIM 12 s: p99 13-19 ms (A) -> 3.2-3.7 ms (GI8P0E) / 7.0-16.3 ms (F), and the means stay 1.0-1.7 ms: ~10 % of TIM grants are large
    (64QAM / 2-layer on up to 273 RB) and take 1.5-2 ms in demod on the GPU itself (`GPU_EXACT_DEMOD gpu 425 us` mean).
  - What is left on b (final arms): fep ~100, chest ~135, demod ~210-320, ldpc ~145-180 us. Quiet windows reach
    495-565 us; the rest is RT-vs-RT contention (5 PDSCH consumers + PDCCH on the same SMs) and ~7 us per kernel launch
    x ~20 launches per decode (see "What remains").
* **Root cause of the "PDSCH waits behind discovery" picture (DECGPU): three separate mechanisms, all fixed here.**
  1. *SM occupancy by many-block discovery kernels*, not the long few-thread ones. `[MEASURED, nsys replay b]` an RT
     kernel running while a CSI-RS `sweep` (up to 4096 blocks x 128 threads, full occupancy) is resident takes **24x**
     its median (p90 68x); while `segment` / `refine_kernel` / `energies` / `finish` (1-280 blocks, 1-32 threads) run,
     **1.6-2.3x** = the same as with no discovery kernel (1.9x, RT-vs-RT). The 600 ms `refine_kernel` holds one SM,
     not the GPU. Fix: green-context SM partition (`ISAC_GPU_DISC_SMS`, `ISAC_GPU_RT_ISOLATE`): sweep-time slowdown
     24x -> 2.2x.
  2. *The GPU LDPC wait.* `cudaStreamSynchronize` under `cudaDeviceScheduleBlockingSync` (set by nr_gpu_platform):
     nsys 304 us per call for ~175 us of kernel queue+exec. Fix: poll like the demod/FEP waits.
  3. *Device-wide stalls from lazy CUDA work on decode threads*: the GPU LDPC built each (BG, Z, R) graph on first use
     (cudaMalloc + synchronous cudaMemcpy, up to 69 ms each, ~110 per replay), created its contexts at the first TB
     (569 ms first-TB stall on TIM), and the Nl = 3, 4 MMSE kernels were loaded at their first launch (CUDA lazy
     loading, 44 ms launch stalls in nsys). Fix: all done before RX.
  With 2.+3. the GPU LDPC goes from **357-590 us to 102-122 us per TB** on b with the final binary (110-153 us on
  capture 8 and TIM; 114-125 us on an idle GPU in test_nr_pdsch_gpu_ldpc).
* **`ISAC_GPU_DISCOVERY_BUDGET_PCT` cannot help CSI-RS discovery** `[CODE-READ]`: `nr_gpu_budget` slices only the PDCCH
  NID module (nr_gpu_budget_cuda.h); no CSI-RS discovery kernel goes through it.
* **Bit-exactness: unchanged by construction** (streams, waits and load timing only). `[OFFLINE VERIFIED, DGX GB10]`
  `test_nr_pdsch_gpu_ldpc` mismatches=0 (1,635 snapshots, 264 stop cases); `test_nr_pdsch_gpu_demod`
  DEMOD_MODEL_MISMATCHES total=0 with and without the partition flags; replays: `GPU_EXACT_LDPC check_bad=0`.
* **CSI-RS discovery: same resources, similar time to confirm** `[MEASURED replay]` (table below): b 58-59 distinct
  WINNER resources and 24 confirmed in A and F; capture 8: 81 vs 82-84 resources, 41-47 vs 41-50 confirmed; TIM: 26-27
  (A) vs 20-28 resources (partition arms), 2 vs 2-8 confirmed (TIM confirms little in 12 s in every arm; see Risks).

## 1. Measurements

### 1.1 Where the discovery time goes, and what it does to RT kernels (nsys, b, base t26r)

`[MEASURED, DGX GB10, nsys -t cuda, replay b, base]` GPU time: segment 17 %, energies 12.5 %, refine_kernel 11 %,
sweep 8 %, finish 4.6 %, lattice_screen 2 % (CSI-RS); score 3.2 %, standardize 2 % (PDCCH NID); PDSCH kernels ~35 %.
Kernel durations: refine p50 5.7 ms / max 259 ms (1 thread), segment p50 4.4 / p99 67 ms (<= 280 x 32), energies p50
426 us (1 thread, 3,690 launches), sweep p50 20 us / max 57 ms (up to 4096 x 128).

(the GPU LDPC) for its whole duration once in a while.

## 2. Changes (all default off; flag off = previous behaviour)

* **6f13062d4b fix(build)**: the csd/dec-gpu merge left two PDTIMPCT implementations in `nr_pdsch_passive_decode.c`
  (did not compile). Kept DECGPU's (`PDTIMPCT us ... sum[...]`, parsed by gpudemod_stats.py); dropped dec-queue's 16-us
  `PDTIMPCT calls=` line.
* **41f1196135 feat(gpu-share)**: `nr_gpu_green.h`. `ISAC_GPU_DISC_SMS=N` -> CSI-RS discovery streams
  (`nr_csirs_disc_gpu.cu` DiscoveryStream incl. its cuFFT plans, `nr_csirs_disc_gpu_sweep.cu` workspace) and the PDCCH
  NID stream in a green context on the first N SMs (driver granularity: 8 -> 8 SMs, 16 -> 16 on GB10).
  `ISAC_GPU_RT_ISOLATE=1` -> PDSCH exact FEP/chest streams, GPU demod (both streams), GPU LDPC and PDCCH FEP streams in
  a green context on the other SMs. Without RT_ISOLATE the RT kernels keep all 48 SMs and still share the discovery
  SMs (G16: p99 better, means not). Test `test_nr_gpu_green` (ctest; exit 77 = skipped).
* **a11383e94b perf(gpu-ldpc)**: GPU LDPC polls; graphs for every (BG, Z, R) and both kernels loaded at init; init
  called from `nr_pdsch_gpu_exact_warmup()` (before RX); GPU demod init loads `k_mmse2n<3,4>` / `k_mmse0n<3,4>`.
* Not changed: discovery algorithms/kernels, solver scheduling (`rr-csd-scv`), `nr_pdsch_passive_queue.c`.
* TLS: no new `__thread` data (all new state is static, pointer-sized or per-module).

## 3. What remains to reach < 0.5 ms (not done)

1. **Kernel-launch overhead and RT-vs-RT contention** (largest on b): ~20 launches per decode at 7-8 us each in nsys
   (2-3 us idle), and RT kernels at 1.9-2.5x their median with no discovery kernel resident. Next: one launch per stage
   (fused demod kernels, or CUDA graphs per grant shape), and batching the consumers' grants per slot.
2. **Large TIM grants**: GPU demod 425 us mean / 1.5-2 ms at p90 for 64QAM and 2-layer grants on up to 273 RB; profile
   `k_*` per grant size (ISAC_PDSCH_GPU_EXACT_DEMOD_PROF=1) and parallelise the per-RE loops that scale with RBs.
3. **One-off 30-140 ms stalls** still present in most runs (fep/chest/demod max): not attributed yet (candidates: the
   remaining lazy first launches of other modules, discovery cudaHostAlloc/cudaMalloc at start-up); an nsys of capture 8
   would identify them.
4. Discovery itself: `energies`, `refine_kernel`, `finish` are single-thread kernels (12.5 + 11 + 4.6 % of GPU time); they
   do not slow PDSCH (1.1) but slow discovery; parallel versions (one thread per RB with the same summation order) are
   straightforward.

## 5. Risks

* **Discovery on 8 SMs is slower** on the 273-RB TIM carrier: distinct WINNER resources 20-28 in the partition arms vs
  26-27 in A (same range as P0 without partition, 25-28; TIM confirms only 2-8 resources in 12 s in every arm, so this
  replay cannot settle it). If an OTA run on a 100 MHz cell confirms resources later than with t26r, use
  `ISAC_GPU_DISC_SMS=16` (GIP0 arms) or drop RT_ISOLATE.
* RT kernels get 40 of 48 SMs; RT-vs-RT contention rises slightly (nsys "none" ratio 1.9 -> 2.5 at 32 RT SMs).
* GPU LDPC: `fallback[..., err]` = 0-314 TBs per run (up to ~2 % on b, ~4 % on TIM) are refused by
  `nr_pdsch_gpu_ldpc_run()` before launch (a (BG, R) pair or job shape the port does not build; not broken down) and go
  to the CPU decoder as before; GPU results are CPU-equal (22,000/22,000 in DECGPU, `test_nr_pdsch_gpu_ldpc` here).
* The polled LDPC wait spins one decode core for the TB's ~130 us (as the demod/FEP waits already do).
* Green contexts need CUDA >= 12.5 runtime + a driver exposing the entry points; otherwise the flags log and fall back.
