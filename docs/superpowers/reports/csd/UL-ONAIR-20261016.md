## Summary
UL fails for three stacked reasons, none of which is the RX chain:
1. **Per-UE scrambling identities are unknown.** Where the right (DM-RS id, data id) pair was known, decoding worked at the same snr_db where it failed with the wrong pair.
2. **The BWP vote needs a probe at >= 6 dB DM-RS SNR, and those essentially do not exist** (1 of 3448 probes in TG1). So the lock only comes from votes in loaded runs, or from 2 CRC passes (circular).
3. **Even in the locked run the cache is not filled** by construction (put conditions exclude solver probes and transform precoding).
In addition, a CRC-16 false-alarm floor is the same order as the observed "successes" in the unlocked T runs.

## 1. What must happen for ULLAYOUT to lock, and what fails
Lock chain [CODE READ, nr_pdcch_ul_layout_lock.c]:
- (a) A length bank has >= FIT_MIN=256 DCIs.
- (b) `fit_mcs` finds the MCS/HARQ offset (>= 64 HARQ pairs, score >= 1.2, margin 0.3).
- (c) `fit_prefix` yields the bwp_ind/RIV/TDRA/fh prefix.
- (d) `fit_tail` yields the dai/sri/antenna/srs/csi/beta/init tail, which gives CP/TP, CDM and DM-RS add_pos.
- (e) k2 is inferred per TDRA row from the slot occupancy histogram (k2=0 means the fit is rejected).
- (f) Only then the BWP start/size: probes (<= PROBE_MAX_RB=16 PRB) vote when their best hypothesis has DM-RS MRC SNR >= VOTE_DB=6 dB. A lock needs LOCK_MIN=6 votes, leader >= 2x runner-up, >= 2 RNTIs.
- (g) Alternative path, ULLAYOUT_CRC_LOCK: 2 CRC passes in different slots (p_false < ~0.003).
TA is not part of the lock (`ta=1600` nominal in 80 % of attempts, `delay` estimated per grant).

## 2. TG1 (LOCKED 217@0): 3 CRC-OK and put = 0
Timeline [MEASURED, TG1]:

- OK#2 at t=163804: tbs 301. Evidence 2 gave `p_false=0.0029 -> LOCK` and `CRC_LOCK` at abs=163808 (crc_ok=0, trials=15282). So the lock was **caused by** OK#2 and was circular.
- OK#3 at t=239115: tbs 301.
- After the lock only 1 more OK followed, although `0x4f52` had 4717 attempted slots, 13558 attempts with the right ids, and about 2490 slots with MCS 0-2.

Why `put = 0` [CODE READ, nr_pusch_passive_decode.c:2918]: `ul_hyp_store` runs only if `!t_solver_probe && !cfr_only && !gapped && !fdra_unresolved && epoch && !g->transform_precoding`. Candidates, each unverified:
- (i) The locked tail is TP ("init=0 TP cdm=2"), so `!transform_precoding` fails for every OK. This is the most likely cause, since tbs and PRB counts 26/301 and 212+2/5+50/56+50 are all valid TP sizes.
- (ii) OK#1/#3 came from the solver probe path (`nr_pusch_passive_decode_probe`, which never stores).
- (iii) GPU-pass cache `miss=30171`: the cache needs a stored hypothesis, so it can never hit if nothing is put.

## 3. Wrong parameters or SNR?
**Parameters, first.** Evidence from the V reference run `ab_G1_1_234131` [MEASURED, DGX OTA V LOW LOAD 2026-10-15 night, n=1]:
- RNTI 0x4a56, 3391 log lines. With ids (dmrs 249, data 324) **23 of 23 attempts decoded** (mcs 17, 141 bits, 3 PRB, identical payload at 23 different slots and PRB starts). Median snr_db -6.7, range -2.6 to -14.3.
- With the wrong pair (dmrs 415 = PCI, data 8/9/93/95 = sweep candidates) 0 of 52 decoded. Median snr_db -7.1.
- So **snr_db does not discriminate** between decodable and undecodable attempts; the identity pair does. dmrs_id 249 equals the DL PDSCH DM-RS id estimated for the same cell ("DMRS_ID per-CORESET ... DECIDED 249"), while the PCI-default pair fails.
- All 7 CRC-OK on T this window carry non-default data ids: 538 (TG1), 573 (TG2), 472 (TF1), never PCI 923. UL dmrs ids 1931/923/0 differ per run.
- Per-UE data id sweep [CODE READ, nr_pusch_solver.c plan]: starts only after >= 64 grants of an RNTI, tries one id per planned grant, 1024 candidates, probe-class grants only (single code block, QPSK, <= 48 PRB). C-RNTIs rotate, so most UEs never finish the sweep. Expected hit rate is about attempts/1024, the same order as the observed 1e-4.

**CRC false-alarm floor** [CODE/ARITHMETIC]: TBs <= 3824 bits use CRC-16, so P_FA = 1.5e-5 per attempt. At 10k-23k attempts per run that is 0.15-0.35 expected false passes per run, against the observed 0-3. Two of the 3 TG1 payloads are random-looking. In the V reference run the first confirmed id (`n_id=426`, one OK) disagrees with the later 22 OK at id 324 for the same RNTI, so it was probably a false latch. The cell-wide latch at the first CRC pass (`g_ul_data_id`) is therefore not safe.

**SNR.** At the attempt level (status=1, n=17362 in TG1): snr_db < -9: 40 %, -9..-6: 42 %, -6..-3: 15 %, > -3: 3 %. These are maxima over wrong hypotheses, so they look like the noise floor for most attempts. For the right-ids UE `0x4f52` (4164 slots), the best snr_db per slot in MCS 0-2 slots is -9..-6 in 1254 slots, < -9 in 1138, -6..-3 in 98: **3 OK of 2490**. UL SNR is low, but snr_db is not calibrated to Es/N0 and the V data shows decode at -14 dB with the right ids, so a "decodable fraction" cannot be computed from it. Only a bound is possible. Grants with MCS >= 3 in that slot set: 1500 of 4164 (36 %), and almost all UL traffic here is MCS 0-10 with large PRB counts. The only OKs were low-rate (tbs 26-301 bits).

**Waste** [MEASURED, TG1]: 19 % of attempts (4475) are rejected at once ("transform precoding with N_RB not 2^a3^b5^c"). 5.9 % are all-zero TBs (noise-only LDPC convergence). Stale drops are 11-16 % in heavy T runs (lag 57-68 slots against 5 allowed).
