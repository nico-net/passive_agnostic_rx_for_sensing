# GPUALLOC-20261012 -- PDSCH-vs-PDSCH GPU contention, and the Nl=3 demod mismatch (branch csd/gpu-alloc, base csd/otatest 8b7ceae5ad)

Evidence labels: [M-replay] = DGX GB10 aarch64, 4 RX, `timacq_replay.sh SPEED=1`, `ota/t26z.env` (single line, default OTA env at 2026-10-12 15:xx; includes RATELIMIT + NORM_COALESCE + `ISAC_PDTIM_CLASS=1` added by me in every arm), all builds/replays via heavy.sh. [M-nsys] = nsys `-t cuda`, one run per arm. [M-offline] = dump + host/GPU harness. [INF] = inference. Captures not merged: b = raw_pci415_12s_b (SSB 1171, FO 6900), tim = raw_pci923_tim_12s_tile3 (SSB 233, FO -4800). Raw rows: `gpualloc_data/`.

## Verdict
* **Target (per-decode mean < 0.5 ms): not met.** Real-grant mean 0.73-1.08 ms on b, 1.0-8 ms on tim in every arm; p50 0.43-0.55 ms. The mean is set by tails and by single 90-300 ms stalls per run (PDTIMCLS max 24-306 ms in every arm, also base), which no allocation flag touched.
* **New knobs (default off, flag-off path unchanged):** `ISAC_GPU_RT_PARTS=P` (needs ISAC_GPU_DISC_SMS + RT_ISOLATE): the real-time SMs are split into disjoint green contexts, pool context i goes to group i % groups. `ISAC_PDSCH_GPU_CTX_LIMIT=N`: only the first N FEP/demod/LDPC pool contexts are handed out.
* **Finding:** DECTAIL's "one stream per consumer" already exists (8 contexts per stage, DEMOD_POOL_WAIT = 0 in all runs here too). The PDSCH-vs-PDSCH queueing is SM sharing, not stream serialisation, so more streams cannot help; the evaluated levers are SM partitioning (P2) and concurrency limiting (C4). Priority/real-first ordering was already shown null (DECTAIL 1).
* **Result [M-replay, 3 runs/arm, noisy]:** RT_PARTS=2 (RT 40 SMs -> 2 x 16 used) is the only arm that is not worse than RL on both captures: b real mean 821 us (RL 997, base 863), b p99 4.9-6.0 ms (RL 6.3-15.5, base 4.0-11.7); tim real mean 1.2/3.3/1.1 ms (RL 2.0/3.1/2.7). Differences are inside the run-to-run spread (single runs differ 2x on tim); NOT claimed as a win, needs more runs. CTX_LIMIT=4: no benefit (b p99 3.9-12.2 ms, one run 10 % stale); not recommended.
* **Bug found and fixed (bit-exactness):** the Nl=3 GPU demod mismatch exists WITHOUT ISAC_PDSCH_GPU_CHEST_TRIM (control, below). Root cause: CUDA `hypot()` used for the non-integer `cabs()` in the Gauss-Jordan pivot choice differs by 1 ulp from glibc's, flipping a pivot tie; the exact result was a .5 tie (-16.5) so the CPU rounded to -16 and the GPU to -17. Fixed by porting glibc 2.35+'s FMA hypot kernel. CHEST_TRIM is therefore not implicated and may be enabled (perf still unmeasured).

## 1. Demod mismatch control [M-replay, b, t26y, DEMOD_CHECK=1 every call]
| run | trim | result |
|---|---|---|
| ctlNT1 | no | **MISMATCH rnti 0xce76 Qm 4 Nl 3 llr[108301] gpu -67 cpu -66** after 17,997 ok, GPU demod disabled |
| ctlNT2 | no | 8,000+ ok, none |
| ctlT1, ctlT2 | yes (+CHEST_CHECK=1) | 16,003 / 22,000 ok, none |
So the mismatch is pre-existing (earlier DECTAIL case: Qm 6, same Nl 3). Rate ~1 per 2e7 RE.
Reproduction [M-offline]: a temporary dump (not committed) of G, b and the CPU output for every Nl=3 mode-2 RE (1.0 M RE, b and tim) fed to the GPU Gauss-Jordan in a harness (`gpualloc_data/mmse_dump_harness.cu`): 31 mismatching RE (all one matrix with G33 = 0, exact result -16.5, 9.9375), operand-order variants of the multiply/eliminate steps made it worse (1.7-5 k), the hypot variant fixed it: glibc FMA kernel / sqrt(fma(x,x,y*y)) / correctly rounded: **0 mismatches of 1,000,808 RE**. Fix verified [M-replay] with DEMOD_CHECK=1: b 20,000 and 12,000 grants and tim 4,000, check_bad 0, no mismatch (too few to prove by itself; the offline result is the evidence). Note: this changes GPU results for such ties (to match the CPU), so it is not flag-off byte-identical; it is a bug fix. The Nl=2 and mode-0 paths share `cabs_c` and get the same fix.

## 4. Not done
* Batching same-slot grants into one launch and per-consumer priority streams were not implemented (priority/real-first already null; per-consumer streams already exist). Largest remaining item: fewer launches per decode (fused FEP/chest kernels) and the 90-300 ms one-off stalls.
* More runs (>= 6/arm) are needed to decide P2; GB10 has 48 SMs, the driver granularity gives 2 x 16 of the 40 RT SMs (8 idle). Untested: DISC_SMS=16 + P2 and P3.
* Did not pursue SM-share retuning of ISAC_GPU_DISC_SMS (GPUSHARE measured 8 vs 16).
* A first partial series under t26y (4 control + 10 arm runs) is in `replay_t26y_partial.txt`, aborted when the coordinator moved the base env to t26z.
* Scratchpad hygiene: my helper files were written into the shared scratchpad dir (some pre-existing names like results.txt/build.sh may have been overwritten); later ones are under `scratchpad/gal/`.
