# OTATAIL-20261013 — on-air PDSCH decode fat tail vs concurrent GPU discovery

Branch `csd/ota-tail` (worktree `rr-csd-ota`, from `csd/otatest` 2a04ca8145). Build `build_t26` (CUDA, DGX GB10).
Labels per PROJECT_MEMORY §0.1. OTA logs are the orchestrator's runs of 2026-10-13 (Vodafone PCI 415, DEIB), read
offline here; no radio was used by this work. Replays are `[MEASURED, DGX replay raw_pci415_12s_b, SPEED=1, 4 RX]`.
Cells and hosts are never merged.

## 1. Verdict

1. **The on-air > 20 ms bodies are not spread over the run: they come in bursts, and the largest burst sits inside a
   CSI-RS discovery sweep.** `[MEASURED, DGX OTA 2026-10-13 08:58 ab_I2_1_085825]` 35 of the 84 slow bodies of the run
   fall in one 0.8 s window (t = 95.3-96.1 s); 31 of them are chest-bound (chest 30-105 ms each, fep/demod/ldpc
   normal, wall ≈ thread CPU). The window opens right after `CSIRS_DISC HYPOTHESES n=112 sweep=16` (a GPU sweep over 112
   hypotheses) and two `CSIRS_DISC WINNER` lines land inside it; the CSI-RS rate limit had gone STABLE 2.5 s before
   (92.9 s) and went back to SEARCH (new-pattern, 12354 skipped) 2.5 s after (98.6 s). The nID sweep was in
   `MAINTAIN` with pass 36/37 kernels at 178-201 ms (normally 1.7 ms).
2. **Both discovery paths run at full duty on air for the whole run, so a bin-level correlation cannot discriminate.**
   `[MEASURED, DGX OTA 2026-10-13, I1/I2/H0a/H0b/B415a]` CSI-RS discovery (FEP / HYPOTHESES / WINNER) is active in 95-100 %
   of the 1 s bins; the nID GPU sweep runs 37-90 passes per run back to back (0.5-6 s of pass time per 5 s of wall), and
   its kernels stretch from 1.7 ms to 100-234 ms in 30-43 passes per run. Cause of the continuous nID load
   `[CODE-READ]`: `ota/t26bI.env` sets `ISAC_PDCCH_NID_GPU_RECHECK_MS=250` (code default 10000). `nr_gpu_discovery_due()`
   makes a PAUSED (published and verified) sweep due again every `recheck`, so with 250 ms the "pause" after a verified
   CORESET is shorter than one pass: the sweep never pauses (passes 14-19, 22-24 of I1 ran in state PAUSED).
3. **The nID kernel slow-downs (100-234 ms for 1.7 ms kernels) are the symptom of the shared 8-SM discovery partition,
   not an RT effect** `[CODE-READ + INFERRED]`: CSI-RS discovery streams and the nID stream live in the same 8-SM green
   partition, so a CSI-RS `segment`/`refine`/`normalize` kernel queues the nID kernels behind it. The nID path is the
   only one that goes through the GPU discovery budget (`nr_gpu_budget.c`, slices never start while an RT job is in
   flight, 30 % duty); **no CSI-RS discovery kernel or copy went through it** (GPUSHARE already noted this). On air
   the CSI-RS discovery therefore launched sweeps, refines, normalizes and multi-hundred-MB grid uploads regardless of
   PDSCH work in flight.
4. **The green-context partition is in effect** `[MEASURED, DGX replay b, GPU_GREEN_VERIFY]`: `%smid` read from the
   RT stream and from a discovery stream gives `rt_sms=40 disc_sms=8 overlap=0` (48 SMs). The same check now runs
   on air with `ISAC_GPU_HEARTBEAT=1`; `[NOT MEASURED ON AIR]` until the next OTA.
5. **Whether the chest stalls are SM contention or a device-wide stall (HMM translation invalidation, launch
   blocking) cannot be decided from the logs** `[HYPOTHESIS]`. Chest is the only PDSCH stage whose kernels read and
   write host memory in place (direct mode: `rxF`, `pil`, `out`, scratch through the host page tables); demod and LDPC
   work on device copies; the FEP in the same bodies stayed at 60-90 us. A device-wide stall would also slow the nID
   kernels at the same time, which the logs show (item 1), but those are explained by item 3 as well. The heartbeat
   probe (section 4) separates the two on air: a dev-only probe and a host-memory probe on an RT stream.
6. **Replay reproduces the partition and the discovery load but not the on-air bursts** (section 5). Under the gate the
   discovery-driven PDSCH stale drops vanish in replay (0-10 % vs 27-32 %), time-to-first-bank is unchanged with the
   nID-first rule, CSI-RS discovery slows (confirmed at 30 s: 9-16 vs 17-23). p99 moves within the replay spread.

## 4. What the heartbeat tells on air

| GPU_HEARTBEAT during a PDTIMSLOW burst | reading |
|---|---|
| dev and host probes both > 5 ms wall, gpu_ms small | launch/API blocked device-wide (driver lock, module load, allocation) |
| dev and host probes both > 5 ms, gpu_ms ≈ wall | the RT partition itself is stalled (device-wide stall: page fault, TLB shoot-down, context switch) |
| host probe slow, dev probe normal | host-memory path (HMM / C2C) stalled: chest-specific mechanism; try `ISAC_MALLOC_NOTRIM=1` |
| neither slow | not a GPU stall: PDSCH-specific (RT-vs-RT queueing on the 40 SMs, consumer-side) |

`GPU_GREEN_VERIFY overlap=0` with `rt_sms=40 disc_sms=8` confirms the partition; anything else means the split is
not in effect on that host.

A alone spans p99 2.0-4.3 ms and stale 4.6-31.9 %):
- The budget gate removes the discovery-driven PDSCH queue stale drops: stale 0-10 % in all five B runs vs 27-32 % in
  four of five A runs. Real > 20 ms bodies: 0-4 per B run vs 0-3 per A run (no difference in replay; the on-air bursts

  not claimed.
- Cost: CSI-RS confirmations at 30 s drop from 17-23 to 9-16 (the CSI-RS share of the GPU falls to what the 30 % budget
  leaves after the nID sweep), and the nID sweep runs 2-5 passes instead of 35-41 (in MAINTAIN it gets the budget only
  between CSI-RS slices; the published bank is unaffected). The nID worker spins while CSI-RS holds the slot:
  `discovery_yields` 16-22 M vs 1.8-3.5 M per run (its own core 13 on air).
- Without the prefer rule (B1-B3) the CSI-RS acquisition burst starved the nID sweep: first pass +10.6 / +15.7 / +19.2 s
  vs +5.2-8.2 s in A, and B3 published so late that it decoded 1444 grants instead of 4000-10000. With the rule (B4-B5)

- `GPU_GREEN_VERIFY rt_sms=40 disc_sms=8 overlap=0` in all ten runs. Heartbeat: every > 5 ms probe (10-14 per run) is
  in the first 1.5 s after the FEP init (module loading, 222-405 ms launch blocking: the GPUFUSE start-up class), none
  in steady state, dev or host; host probe max 14-29 ms at start only. The replay therefore shows no steady-state
  device-wide or host-path stall; the on-air chest bursts are not reproduced by the replay load.
- `GPU_EXACT_CHEST/DEMOD check_bad = 0` in all runs. CRC-OK counts are not comparable across runs (n of decoded grants
  varies 1.4-9k with the acquisition timing).
