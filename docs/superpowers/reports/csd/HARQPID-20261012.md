# HARQPID (2026-10-12): stage-2 DCI 1_1 grants carried harq_pid = 0 -- bug found and fixed (flag, default off); NO effect on RVRESCUE / MCS 0-4 CRC in replay

Host DGX GB10, worktree rr-csd-drv (csd/dci-layout-rv + 8b7ceae5ad merge), commit 4ad76fa955. build_gpu (CUDA) via heavy.sh. No OTA, no captures.

## Root cause [CODE-READ + MEASURED, replay DGX]
`nr_dci11_layout_to_field_bits()` (nr_pdcch_dci11_layout_sweep.c) hands the layout to the extractor with `harq_pid_bits = 0` and puts the whole
blob tb2 + harq(4) + dai + pdsch_to_harq into `tb2_bits`. `nr_pdcch_blind_extract_11()` then reads the pid with 0 bits, so `out->harq_pid`
= 0 for EVERY stage-2 / solver-planned grant (job.grant.harq_pid, dlsch harq_process_nbr, harq_pid_tag, nr_harq_init_tx key, EVMGRANT pid=).
The DCIRV scorer (`solver_hq_of`) reads the pid straight from the payload (rv+2, 4 bits), so it was right: scorer and decode path disagreed.
Replay pre-fix: EVMGRANT pid=0 on all 4378 grants of tile3 on5 (10 RNTIs).

## Fix (default off: ISAC_DCI11_HARQPID=1)
In layout_to_field_bits: harq_pid_bits = 4, tb2_bits = 0, dai_bits = pre_ant_variable - 4 (total width unchanged, DCI size check and ant-port
offset unchanged; tb2 assumed absent, same assumption as solver_hq_of). Unit test Dci11Handover.HarqPidIsHandedOverAsFourBitsWhenEnabled;
[OFFLINE VERIFIED, DGX] test_nr_pdcch_dci11_layout_sweep 42/42. [MEASURED] with the flag EVMGRANT pid takes all 16 values (e.g. 1493/1320/1440/1101 ... grants) on tile3.

Replay variance (which RNTIs the solver commits to) is as large as any arm difference; on tile3 the arms are indistinguishable
(RVRESCUE means 26 / 27 / 18, CRC 93 / 91 / 91 %). Conclusion: the pid=0 bug is real but is NOT the cause of the tile3 RVRESCUEs or of the
~50 % MCS-0 pass rate in replay; HARQ buffer aliasing is not what makes rv=1 fail. [HYPOTHESIS, unchanged] remaining suspects: TBS / rate-matching /
CSI-RS 16-port (rr-csd-cps area). Why little effect is plausible: rescued grants are mostly first-seen rv=1 (the earlier transmission was never decoded or
never seen), so there is no soft buffer to mix up; and MCS-0 passes are dominated by a single pid per RNTI at low load. Not proven.

## Do keep
The fix is correct on its own (soft combining and NDI tracking now keyed by the true pid; fewer false HARQ merges when several processes are active,
more likely to matter at high load / OTA with real retransmissions). Recommend enabling ISAC_DCI11_HARQPID=1 for the next OTA, not as a lever for RVRESCUE.
