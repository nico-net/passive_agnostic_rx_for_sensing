# MMSE3GPU (2026-10-14): exact 3-4 layer MMSE (mode 3) on the GPU, bit-exact with the CPU

Host DGX GB10 aarch64. Worktree `rr-csd-mmse3gpu`, branch `csd/mmse3gpu` (from `csd/otatest` 4ffe68016c). Build `build_t26`.
Builds and tests ran under `flock -s heavy.lock`. Replays ran one at a time through `heavy.sh` (`flock -x`) with a private
`CUDA_MPS_PIPE_DIRECTORY`, using `timrank34_data/rp.sh` (SPEED 0.5, 4 RX). Other agents shared the host, so every timing number is
`[MEASURED, DGX replay, shared host]`. No OTA was run.

## 0. Verdict

| question | answer | evidence |
|---|---|---|
| Why did the GPU refuse mode 3? | `refuse()` in `nr_pdsch_gpu_demod_host.c` returned `RF_NL` for every mode-3 grant (TIMRANK34 had made mode 3 CPU-only). So the whole `nr_rx_pdsch()` of those grants ran on the CPU. | `[CODE-READ]` |

| Agreement with the CPU double reference | **Bit-exact.** Unit test: 0 of 1,078,272 int16 outputs differ. Replays with CHECK=1: TIM 12000/12000 and Vodafone 21999/21999 grants `check_ok`, `check_bad=0`, 0 MISMATCH. | §2 |

## 1. What changed (all behind default-off flags)

- **`nr_mmse_exact.h`**
  - Contains the whole mode-3 algorithm:
    - `nr_mmse_exact_re()`: Cholesky solve.
    - `nr_mmse3_re()`: per-RE output: z = x/[A^-1]_ll x gain, thresholds w q/32768.
    - `nr_mmse3_gain()`.
    - `nr_mmse3_symbol()`: the CPU symbol loop. It is the former body of `nr_dlsch_mmse()` mode 3, moved here unchanged.
  - Every arithmetic function compiles for the CPU with `noinline, optimize("fp-contract=off")` and for nvcc as
    `__host__ __device__`. The demod `.cu` is already built with `--fmad=false`.
  - Both sides therefore run the same correctly rounded IEEE `+ - * / sqrt` sequence, which is why the results are bit-exact.
  - `[CODE-READ, objdump]` the CPU objects of `nr_mmse_exact_re`, `nr_mmse3_re` and `nr_mmse3_gain` contain no
    `fmadd`/`fmsub` (838 / 162 / 15 instructions).
- **`nr_dlsch_demodulation.c`**
  - Mode 3 now calls `nr_mmse3_symbol()`. The `MMSE3CAL` diagnostic is unchanged.
  - The only arithmetic change is on the CPU mode-3 path: no FMA contraction. That is a 1-ulp-level change in double before
    int16 rounding. Other modes are untouched.
- **`nr_pdsch_gpu_demod_host.c`**
  - `refuse()` resolves `qam_mode` exactly as `nr_rx_pdsch()` does. With `ISAC_PDSCH_GPU_EXACT_DEMOD_MMSE3=1`, mode 3 (Nl 2-4)
    is accepted; with it off, the old `RF_NL` refusal stays.
  - The job carries `m3_nvfac = pow(10, ISAC_PDSCH_MMSE_EXACT_NVAR_DB/10)`, from the same env and the same libm as the CPU.
  - `mag_per_layer` is set for mode 3 (CPU: `qam_mode >= 2`).
- **`nr_pdsch_gpu_demod.cu`**
  - `k_mmse3_prep` (one block per symbol):
    - The strongest layer's sum |h|^2 is computed in int64. It is exact, and so is the CPU's double sum.
    - The ZF residual of every 4th RE is computed in parallel and then summed **by one thread in RE order**, as the CPU loop
      does. This gives s2 and the gain bit for bit.
  - `k_tail<6/7/8>` run `re_mmse3<NL>` per RE, which calls `nr_mmse3_re()`.
  - The kernels are pre-loaded at init, so the first mode-3 grant does not pay CUDA lazy loading.
- **CHECK unchanged:** `ISAC_PDSCH_GPU_EXACT_DEMOD_CHECK` compares mode-3 grants bit-exactly (LLR, comp, mags,
  log2_maxh, EVM), like every other GPU-demod grant.
- **Not on the GPU:** the `ISAC_PDSCH_MMSE_EXACT_CAL` diagnostic line (CPU only).

## 2. Agreement with the CPU double reference

- `[OFFLINE VERIFIED, DGX GB10, test_nr_llr_norm MmseExact.GpuMode3BitExact]`
  - Setup: synthetic 13-symbol grants with 4 RX, Nl 2/3/4 x Qm 2/4/6/8 and 288 REs per symbol. The channels are Rayleigh at
    120/90/40/20 LSB per layer with a frequency rotation; the noise sigma is 3-6 LSB.
  - The full GPU demod (`nr_pdsch_gpu_demod_run`) was compared with `nr_mmse3_symbol()` at the GPU's log2_maxh.
  - Result: **0 of 1,078,272** comp/mag/magb/magr int16 outputs differ.
- `[OFFLINE VERIFIED, MmseExact.Mode3SymbolKnownNoise]` 4 RX, sigma 4 LSB:
  - Nl=3: s2 0.529 against the true 2 sigma^2/2^shift = 0.500; sign errors 0/3600.
  - Nl=4 (s2 from nvar x 10^2.1): sign errors 227/4800, all on the 20-LSB layer of a square Rayleigh channel.
- `[MEASURED, DGX replay tim (raw_pci923_tim_12s_tile3), run tim_C1, CHECK=1 on every grant]`:
  - `GPU_EXACT_DEMOD calls=12000 check_ok=12000 check_bad=0`, refused nl = 0, 0 MISMATCH.
  - Rank 3/4 grants in this run: Nl3 1100, Nl4 7006.
- `[MEASURED, DGX replay b (raw_pci415_12s_b), run b_C1, CHECK=1]`: `calls=22000 check_ok=21999 check_bad=0`, 0 MISMATCH.
- EVM (GPU float sums, as before): `evm_far=0`, maxrel 3.3e-6.

## 7. Open risks

- **CPU mode-3 numerics changed by ~1 ulp.** The CPU mode-3 path now runs without FMA contraction. The TIMRANK34 tests still
  pass, but this is the CPU result of a flag-off path that could flip one int16 in ~1e13. No CRC effect is expected
  (`[HYPOTHESIS]`).
- **`noinline` CPU call per RE.** The CPU mode-3 cost per RE is unchanged within noise: `tim A` demod mean is 1.36-1.61 ms vs
  1.53-1.58 ms in TIMRANK34. This is not separately measured.
- **CHECK cost.** CHECK=64 keeps a CPU mode-3 reference on ~1.6 % of grants, which sets the demod p99 (2.4 ms on TIM). A
  sparser CHECK (e.g. 256) would cut that tail but weakens the on-air guard. That is the orchestrator's call.
- **0.5 ms decode p99 not met.** Chest and LDPC p99 remain. This port removes mode 3 from the tail; it does not solve the whole
  tail.
- **s2 for Nl == nbRx** still uses `ISAC_PDSCH_MMSE_EXACT_NVAR_DB` (TIMRANK34 known issue), identically on CPU and GPU.
- **Item 2 of the task (NEON / per-PRB Cholesky on the CPU) was not done.** The GPU port made it unnecessary for the
  default path, and a per-PRB solve would break bit-exactness with the GPU.
