# FATTAILS-20261014 -- PDSCH decode fat tails: sources, fixes, core-6 plan (branch csd/fattails, base csd/otatest c23cc9e213)

Host DGX GB10 (aarch64, CUDA sm_121). Evidence labels (PROJECT_MEMORY §0.1). Cells never merged: `b` = Vodafone PCI 415
(`raw_pci415_12s_b`), `tim` = TIM PCI 923 (`raw_pci923_tim_12s_tile3`). Replays = `tests/passive_rx/p99_replay.sh` (air-like:
sudo, FIFO-pinned OTA core map, real-time raw_iq), env `ota/t26e.env` + `ISAC_SCANCOST=1` in every arm, one replay at a time under
`heavy.lock`, private `CUDA_MPS_PIPE_DIRECTORY`. **No OTA was run.** Replays cannot reproduce the OTA load (DPDK producer, 150 s
of live traffic, the higher daytime grant rate); every number below is `[MEASURED, DGX replay ...]` unless labelled otherwise.

## 1. Verdict

- **Target "whole-decode p99 < 0.5 ms for all MCS and layer counts": NOT MET.**
  - The floor is per-grant work.
  - A single decode pass ("body") has p50 0.34-0.47 ms. Every grant that fails CRC runs recovery passes, and with them the whole
    decode call has p50 1.0-1.5 ms.
  - Sub-0.5 ms whole-call p99 would need CUDA graphs or a fused chest+demod launch, and recovery work moved off the grant's
    critical path. Neither was done here (section 6).
- **The fat tails (tens of ms up to 1 s) are explained and removed in replay.** Whole-decode max went from 744 ms to 27 ms (b) and
  from 995 ms to 15 ms (tim). p99 went from 20.0 to 5.2 ms (b) and from 48.2 to 6.9 ms (tim). CRC-OK counts were not lower in any
  MCS bucket or layer class (section 4).
- **Bit-exactness is kept.** The async checks ran every grant (`ISAC_GPU_CHECK_ASYNC_EVERY=1`) with a CPU-only reference.
  - b: demod 3799 / chest 4742 checks, `check_bad=0`.
  - tim: demod 4744 / chest 4658 checks, `check_bad=0`.
  - 0 GPU MISMATCH lines.

## 5. CPU / GPU budget

- **GPU.** `gpu_budget_used_pct` is unchanged: b 19.8 % (O) vs 19.7 % (F); tim 22.7 % vs 22.1 % (`ISAC_GPU_BUDGET=1`). The
  check worker issues no GPU work. Pinning adds ~1 MB pinned per consumer thread.
- **New threads.** Two new threads, `gpuCheckBg` and `dmrsIdBg`, both SCHED_OTHER nice 19, never pinned to a big or RT core. No new
  RT priority, no busy-spin.
  - `gpuCheckBg`: ~1 % of a little core at every-256. The worker takes 1.4-2.3 ms per check (max 63 ms) and dropped 0 checks
    at every-256.
- **Per core** `[MEASURED, DGX replay b, perf sched 8 s; before = inline checks + PUSCH on core 6, after = F]`:
  - core 6: scan 47 % + PUSCH 34 % (19 % idle) -> scan 47 % (53 % idle).
  - core 0: idle 98 % -> PUSCH 74 %.
  - PDSCH consumers: 8-12 % -> 15-18 % each (more grants decoded, no stale drops).
  - PDSCH-consumer CPU on tim (profile samples): -62 % with `DMRS_ID_ASYNC`.
- **UL cost.** UL decode tries per run were not lower (b 734 -> 720-869, tim 829 -> 702-903), but the PUSCH decode takes longer on
  a little core at SCHED_OTHER. Mean `UL_PUSCH_CRC cpu_us` went from 9.0-9.5 ms (core 6 FIFO 30) to 20-29 ms (core 0).
  - UL CRC-OK is 0 in every replay arm, so the CRC effect is `[NOT MEASURED]`.
  - This UL latency cost is the price of the core-6 plan. The UL agents' own plan (cores 0,1, GPU FEP) is the place to recover
    it. Do not put an RT UL thread back on a core shared with a FIFO-50 scan consumer.

## 6. What sub-0.5 ms whole-call p99 still needs (not done)

1. Recovery work off the critical path: return the first-pass result and run the arms on a lower-priority stream/thread, publishing
   a late rescue.
2. One CUDA graph per (stage, grant shape), plus fused chest+demod. A body is ~17 launches today, and its p50 is 0.34-0.47 ms.
3. The deferred EVM wait sits outside the stage timers and is the largest off-CPU wait of a normal body (perf: 10k sleeps per 8 s).
   The EVM is needed by the SNR gate and EVMGRANT.
4. The CPU-chest probes of source 7.
5. PDSCH consumer 0 off scan core 7, once a free big core exists.

## 9. Risks

- Async checks validate a grant after its result is used. A MISMATCH disables the GPU path 1-60 ms later than inline did, and the
  grant(s) in between keep GPU results.
- The worker reference uses CPU delay, not GPU delay. It was bit-equal on ~18k checks (section 1), but this is a stricter
  reference than before.
- `DMRS_ID_ASYNC` drops ~22 % of the per-CORESET DM-RS id observations on tim, which can slow an id decision.
- `RETRY_BUDGET_US=1000` skips long-shot arms. Their measured rescue share was ~1 % (P99 report); the replay rescue rate did not drop.
- The core-6 plan raises UL decode latency 2-3x (section 5).
- Replay is not air. The copy-engine and kworker mechanisms are host-independent, but their on-air frequency is
  `[NOT MEASURED ON AIR]`.
