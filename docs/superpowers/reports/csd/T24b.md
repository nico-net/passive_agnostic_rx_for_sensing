# T24b — device regression fixes

2026-10-08, `csd/t24b`, base `9599c54170`, DGX aarch64 sandbox. No GPU,
receiver, replay, or OTA execution. The orchestrator's GB10/X410 observations in
the task are **[MEASURED, supplied evidence]**, not measurements made here.

## Changes and diagnosis

**[CODE-READ] CSI-RS flag-off scheduling.** T24 replaced the asynchronous
antenna/symbol uploads with `disc_copy()` (one completion wait per symbol), and
wrapped every kernel and copy with runtime budget/fence queries. The fix selects
`<false>`/`<true>` host implementations at the module interface. The false
specialization emits direct launches, the original copy/memset operations and
completion boundaries, the 100-slot accumulation/FEP batches, full sweep grids,
and local refinement accumulators. Symbol uploads again enqueue all copies and
wait once. There are no slice events, budget queries or admission waits in the
false per-operation call graph. The budgeted implementation retains bounded
transfers, one-slot FEP/accumulation/refinement, and candidate tiles.

Files: `nr_csirs_disc_gpu.cu`, `nr_csirs_disc_gpu_cluster.cuh`, and
`nr_csirs_disc_gpu_sweep.cu`, under `openair1/PHY/NR_UE_TRANSPORT/`.
`nr_csirs_disc_feed.c` has **no T24 diff** against `aca02df8b2`; its only change
at the task base is T23's core-plan thread-creation hook. It is deliberately
untouched, as are the core planner and all PDCCH DCI decode sources.
The `nr_csirs_disc.h` contract and existing semantics are unchanged.

**[CODE-READ] nID slowdown.** T24's `LAUNCH` called `complete()` after every
kernel; that queued another event and slept in 1 ms increments. After RX,
`slice.run()` had already waited for the kernel, so the second wait was redundant.
Before RX, the algorithm test bypassed slice accounting but still paid those
per-launch waits. The old test therefore did not actually exercise a 30% budget.
It now seals the RX fence when budgeting is enabled. Completed slice timings are
collected without another submission/wait; necessary host dependencies use a
short completion poll. The slice helper no longer polls completion with 25 us
sleeps, nor rounds every short pacing delay up to a 50 us sleep. Pacing credits
the host completion/accounting time already elapsed since admission.

The first-symbol sweep uses its cooperative two-snapshot tile over all IDs,
instead of one snapshot × 4096 IDs (32 launches for the same two snapshots).
Secondary calibration/combination has a 256-ID launch bound, reads the compact
survivor count, and skips empty tail launches. Stage-2 scoring is limited to
32 hypotheses × 32 **active** snapshots, with the original addition/vote order
retained. T24 iterated over every captured snapshot even when the stage-2 active
set was small; those empty tail launches are removed.
These nID work bounds apply with the budget flag off as well as on. The fixed
preallocated timing-event ring drains before reuse, so a large unbudgeted
hypothesis × snapshot plan cannot exhaust its 32,768 event pairs and return -1.
`nr_pdcch_nid_chunks.h` holds the CPU-testable planning constants/tail helper.

**[CODE-READ; device trigger remains unconfirmed] stream `rc=-1`.** A T24 slice
over 5 ms set the process-wide fault flag. The *next* upload/launch then returned
`cudaErrorNotReady`, which became `rc=-1` and permanently stopped the worker.
CUDA events measure the interval between stream markers, including possible
host descheduling between marker/launch submissions; this is not exclusively
kernel execution time. T24b warms the slice events before RX, logs the concrete
operation/CUDA result/event duration, charges the full overrun and its pacing
debt, and retains the overrun counter without manufacturing a subsequent CUDA
failure. Actual CUDA errors still close admission. The device benchmark still
**fails on any overrun**; this is recovery, not relaxation of the 5 ms acceptance
gate. The supplied `rc=-1` alone cannot distinguish this path from a genuine
CUDA error; the exact original triggering operation cannot be proven without
device diagnostics. The new stream run is a required acceptance gate.

**[CODE-READ] RT fallbacks and the contention `errors=1`.** The old atomic
exclusive owner rejected every RT arrival overlapping discovery, so a roughly
30% discovery duty directly caused roughly 30% admission fallbacks. RT now
increments an independent count while the single discovery ownership bit stays
set: high-priority RT streams can enter while an in-flight discovery slice
retires, and the next discovery slice waits until RT retires. This relies on CUDA
block scheduling/concurrent capacity; it does not claim kernel preemption.
The original benchmark's 251 us wait and early stop at 433 jobs identify an RT
deadline timeout. T24's timeout faulted the global arbiter; its background worker
then counted the resulting admission refusal as `errors=1`. That counter did
not establish an independent CUDA execution error. An RT timeout now quarantines
only its RT caller, preserving discovery. The benchmark prints `rt_timeouts`
and actual CUDA failures separately, includes the failed job in `wall_max_us`,
and enforces fallbacks <1%, errors/timeouts/overruns zero, and all 20,000 jobs.

**[CODE-READ] duty state machine.** The monitor sends repeated outside-occupancy
level notifications. T24 reset the acquisition state and `next_us` on every
notification, even with published records. T24b preserves the published
MAINTAIN cadence, treats continuous occupancy as one wake episode (rearmed after
a quiet MAINTAIN interval), and lets bank acknowledgement pause again. Publication
sets MAINTAIN immediately. Record order and diagnostic tie-count changes no
longer invalidate the identity generation/bank acknowledgement. Epoch and capture
geometry changes still reacquire; old-epoch in-flight results are discarded.
`PDCCH_NID_GPU mode ...` logs show ACQUIRE, MAINTAIN and PAUSED transitions and
reasons, independently of the shared budget flag.

**[HYPOTHESIS, not identified by the supplied aggregate log] 168–171 ms kernel.**
The original timing bucket `SWEEP` combines `sweep`, `calibrate`, and `combine`;
a pass-level maximum cannot identify which ran long. The all-survivor secondary
`combine` and full-window `score` launches had data/window-dependent work. They
are now chunked in both modes. An over-5 ms kernel reports its exact launch
expression even with budgeting off (`PDCCH_NID_GPU kernel_overrun`), and budgeted
slices report `GPU_DISCOVERY_SLICE`. Device profiling below is required to name
the original culprit and verify all kernels <5 ms. The existing per-kernel
event brackets can also include a host enqueue gap; a profiler is needed to
distinguish that from actual kernel execution. No unmeasured timing claim
is made here.

## Limits

[IMPLEMENTED, NOT VALIDATED ON DEVICE] The restored CUDA submission schedule is
source-verified, not a GB10 timing measurement. The unchanged T23 core-plan hook
means a whole-receiver timing comparison also depends on the orchestrator's core
map. Numerical parity, CSI-RS confirmations in both modes, ~3.3× budget cost,
<1% RT fallback, and <5 ms kernels all require the following device/OTA gates.
Overshoot recovery deliberately replaces T24's permanent global shutdown; the
full event time is charged, even if it temporarily exceeds a rolling allowance.
A real CUDA failure still stops discovery. There is no unconditional latency
guarantee against OS descheduling, foreign GPU users, or driver stalls.
