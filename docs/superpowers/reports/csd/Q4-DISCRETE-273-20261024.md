## 6. Efficiency, memory and what is not done

- Copies per grant `[MEASURED, census, rank 4]`: demod H2D 1.5 MB (rx span of the data symbols + the referenced estimate rows + geometry) and D2H 2.07 MB (int16 LLRs, rank-4 256QAM: 2.3 MB of LLRs is the decoder's input; comp layer 0 of one symbol for the Qm oracle); chest H2D 0.44 MB / D2H 0.49 MB; FEP (when forced) H2D 0.75 MB / D2H 0.71 MB per call (span-only upload). Pinned host buffers, one async stream per context, 2D copies of only the used spans.
- **Not done: device residency across the standalone stages.** The demod re-uploads the estimate rows the chest just copied back (about 0.5 MB, ~80 us at x4), and the IQ/rxdataF span is uploaded per stage, not once per slot. The device-resident chain FEP -> chest -> demod -> LDPC is the GPUPASS graph (used at rank 1); at rank 4 the pre-existing GrantWork gate keeps grants off it on both tiers. Lifting that gate (`NR_GPU_PASS_GATE_GW`: the owner publishes un-normalised LLRs, the pass returns normalised ones) is the next lever for rank 4 `[HYPOTHESIS]`.
- Not done: a standalone staged GPU UL chest / equaliser / LLR entry (UL grants that bypass the UL pass use the CPU for those stages); UL graph classes for varying grant shapes (3209 of 4156 UL pass runs were `unseen` class misses in ulv_C).
- Not done: Q5 deadline scaling (deadlines stay fixed, user decision); the 768/1536/3072 FFT sizes (no GPU twin, CPU).
- Memory: staging sized from the T6b budget share (2 %), fail closed to CPU with one log line when it does not fit (`GPU_EXACT chest/delay staging unavailable`, `GPU_EXACT_DEMOD standalone staging unavailable`, `UL_GPU_LDPC init refused: …`, `UL_GPU_FEP … staging buffers do not fit`). No OOM in any arm; max RSS 5.7 GB in a 7 GB scope.

## 7. Answer: does the receiver reach sync on the 273 PRB UL tap bed?

Yes, in 5 of 7 starts on this branch; **2 of 7 hung before sync** (ul_A on `208877e485` and ulv_B on `8f7e053986`). Same symptom as the OTA agent's 106 PRB bed: the receiver connects as the tap (`UL-tap client (listen-only, DL+UL combined) from connection #2`, `RFsim: Number of antennas changed from 0 to 1`), creates its threads and then logs nothing more (no `Starting sync detection`), while the gNB and UE run normally (gNB UL CRC 97-99 %). The hung run and the good runs used the same scripts, configs and binary class, so the hang is intermittent, not configuration-specific `[MEASURED, n = 7]`. What differs from the 106 bed: 273 PRB / 122.88 MS/s, `gnb.sa.rfsim.100mhz.conf`, `-C 3750000000 -r 273 --ssb 1478`, `ul_rfsim_rx.273.cfg` (only the CSI-RS monitor width differs from `ul_rfsim_rx.cfg`; same `rfsimulator` `options = ("chanmod")` and AWGN models), `--ue-nb-ant-rx 4`, default `UE_SETTLE=25`. `[HYPOTHESIS]` A start-up race in the tap path (`tap_next` set from `lastWroteTS + 1` at accept, then the first block only when `ts + nsamps - tap_delay > tap_next`) could leave the receiver's first blocking read unanswered; not investigated.
