# BATCHCPU-20261012 -- GPU admission gate and adaptive CPU routing for PDSCH decodes (branch csd/batch-cpu-small, base csd/otatest 51eb8f97ab)

Evidence labels: [M-replay] = DGX GB10 aarch64, 4 RX, `timacq_replay.sh SPEED=1`, `ota/t26z.env` + `ISAC_PDTIM_CLASS=1`, all runs via heavy.sh; captures b = raw_pci415_12s_b, tim = raw_pci923_tim_12s_tile3 (never merged). [INF] = inference. Raw rows: `batchcpu_data/res_v1.txt` (v1 estimator), `res_v2.txt` (v2, host disturbed), `res_v3.txt` (v2, b only). Host load average was 8-11 from non-heavy.lock processes (firefox, python, nearRT-RIC) the whole time.

## Verdict
* **Target (mean < 0.5 ms, no stale drops): NOT met, neither flag achieves it.** Real-grant mean in clean runs 0.75-1.04 ms (all arms), p50 0.43-0.47 ms.
* **Not implemented: a kernel-level batcher.** Fusing FEP/chest/demod/LDPC of many grants into few launches (new CUDA kernels with per-grant parameter tables, bit-exact CHECK modes) was out of scope for this session. `ISAC_PDSCH_GPU_BATCH=1` is only an **admission gate** (see below); do not describe it as batching.
* **ISAC_PDSCH_CPU_SMALL: harmful or neutral [M-replay].** The CPU body of a 16-64 PRB x layers grant measured 1.8-3.7 ms (class log2(PRBxNl)=4-5) against 0.4-1.0 ms on the GPU, so CPU routing only pays when the GPU queue wait exceeds that. v1 (plain EWMA of the body time) was dragged by single 30-300 ms process stalls into routing 14-22 % of bodies to the CPU: b real mean 1243 / 1133 us vs base 994 / 765, probe mean 892-1152 vs 659-793. v2 (samples clipped at 8 ms, 1-in-64 refresh) routes only 0.1-3 % of bodies to the CPU and is then neutral (b run 5: 825 us vs base 1039, batch 793; CPU-routed 683 of 24,000). Conclusion [INF]: on this host the GPU path is faster than the CPU path in almost every state, the 10 % tail is stalls that hit both paths, so the router correctly almost never fires.
* **ISAC_PDSCH_GPU_BATCH=1 (gate): possible tail reduction on b, not significant.** Clean runs, b real mean/p99: batch 752/4255, 827/6895, 793/4095 us vs base 994/11405, 765/4515, 1039/16095 us; probe mean equal. tim (2 runs): batch real mean 2369 / 1916 vs base 3277 / 4213, p50 505 / 715 vs 855 / 585. Counter-example: run 4 (b) batch 1665 us (a disturbed run, 1 s stall, base same pair 728). pdschq drop_stale batch 3.3 %, 0.4 %, 1.3 % vs base 0.7 %, 8.0 %, 16 % (replay values, not OTA's 39-47 %). Gate waits: 1-5 k per run, mean 0.9-1.3 ms, 5-10 % forced through after 3 ms. Needs >= 6 clean runs per arm to claim anything.
* **Run-to-run noise dominates**: about half the runs, in every arm including base (b3, b4), contain ~1 s stalls (max 0.9-1.9 s) with real n halved; these are host disturbances, not attributable to the flags, and were excluded from conclusions (listed in the raw files).

## What was built (all default off, flag off = byte-identical path: one predictable branch)
* `nr_pdsch_cpu_route.[ch]` (new). `passive_decode_body` is wrapped (`passive_decode_body_gated`); four GPU entry points (`nr_pdsch_gpu_exact_fep_ranges`, `nr_pdsch_gpu_chest_grant`, `nr_pdsch_gpu_demod_grant`, `nr_pdsch_gpu_ldpc_decode`) return their existing CPU-fallback code when `nr_pdsch_route_cpu()` (a `__thread bool`). Output is the unchanged CPU chain, so bit-exactness is that of the existing fallbacks (not separately re-verified with CHECK=1 here).
* `ISAC_PDSCH_CPU_SMALL=<maxPRB>` (+`ISAC_PDSCH_CPU_SMALL_NL`, default 2): candidates <= maxPRB PRB and <= NL layers; per size class floor(log2(PRBxNl)) EWMA (1/8) of GPU-path and CPU-path body time; CPU when its estimate is lower; first 4 samples of each arm explored; loser refreshed 1/64. Runs on the consumer threads' own cores (ISAC_PDSCH_CORES), no extra threads.
* `ISAC_PDSCH_GPU_BATCH=1` (+`_SLOTS`, default 3): at most SLOTS bodies in the GPU chain, probes leave one slot to real grants, a waiter stops waiting after its CPU estimate (if CPU_SMALL candidate) or 3 ms. No EDF (deadlines are not visible at this layer).
* Logs: `SENSING: CPUROUTE calls=... cpu=... gate_waits=... wait_mean_us=...` and per-class estimates every 4000 bodies. Hunks in shared files are 2-4 lines each; csd/stalls had no commits at merge time (nothing to merge).
