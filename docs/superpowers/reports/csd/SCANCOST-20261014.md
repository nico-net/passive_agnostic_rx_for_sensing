# SCANCOST-20261014 -- why a blind PDCCH scan occasion costs 1-2 ms, and four bit-exact cuts behind `ISAC_SCANCOST=1`

Branch `csd/scancost` (base `csd/otatest` 4ffe68016c), worktree `rr-csd-scancost`. Host: DGX GB10 (aarch64). Labels per
PROJECT_MEMORY §0.1. `[MEASURED, DGX air-like replay <cap>]` = `tests/passive_rx/p99_replay.sh` (OTA cfg `sd_t26ul.cfg`, scan pool
"2:32:6", SCHED_FIFO pinned threads as on air, env `ota/t26bPQ.env` = the OTA T2/U2 arm), raw_iq at **SPEED=1 (real time)** unless
stated, one replay at a time under `heavy.lock`. Captures, never merged: `b` = Vodafone PCI 415 (`raw_pci415_12s_b`), `tim` = TIM
PCI 923 (`raw_pci923_tim_12s_tile3`). Reference binary R = `rr-csd-b/.../build_t26/nr-uesoftmodem` (mtime 2026-10-14 07:14, csd/otatest
08db255521 code; every R run below was made with this binary, before the orchestrator's 3e82877d68 rebuild). N = this branch with
`ISAC_SCANCOST=1`; O = this branch, flag off. Replays are not OTA numbers; replay scan loss (2-6 %) is lower than on air (16-30 %).

## 1. Verdict

1. **Half of the scan CPU was not the PDCCH decode.** `[MEASURED, DGX air-like replay b, perf record -t <scan TIDs>, R]`: 16 % of the
   scan consumers' cycles sat in one linear search (PDSCH solver offset-key grouping, `run_occasion_one` lines 9315-9316), 12-13 % in
   `getenv()`+`strncmp()` called once per parsed layout (`nr_dci11_layout_to_field_bits`, ISAC_DCI11_HARQPID), ~7 % in a bit-serial
   Gold generator re-run per reading x identity (`dmrs_scan_filter_readings`), 3 % in `nr_dci11_same_reading`. All of it is in
   **Phase 2, under the global Phase-2 lock**, so the second consumer waits for it too. The polar decodes (applyF/G, computeBeta,
   polar_decoder_int16) are ~30 %, FEP+LLR ~10 %.
2. **The 50-230 ms per-occasion maxima on TIM are one call**: `nr_pdcch_ul_discovery_grant -> init_search -> nr_hyp_sweep_init` builds
   the UL field-width hypothesis classes pairwise (O(n_raw x classes x samples) `extract()` calls, ~200-380 ms of CPU) in Phase 2,
   holding the Phase-2 lock: both consumers stop, the queue overflows (`drop_full`). `[MEASURED, DGX air-like replay tim, perf
   script, N before this fix: two stretches of 224 and 380 ms, 194/217 samples in extract < equivalent < nr_hyp_sweep_init]`.
3. **`ISAC_SCANCOST=1` (four bit-exact changes, default off) removes the scan loss in the replay** and cuts the tail, without adding
   threads: b loss 4.7 -> 0.1 %, tim 2.2 -> 0.0 %; occasion p99 5.9 -> 3.4 ms (b), 5.6 -> 3.3 ms (tim); occasion max 53-209 ms ->
   12-14 ms; Phase-2 time per pass 280 -> 97 us (b), 308 -> 75 us (tim). Table in section 4.
4. **Accepted DCIs: no loss found.** N-vs-R set overlap is at or above the R-vs-R run-to-run overlap on both captures, real time and
   half speed (section 5). The four changes are equal-output refactors with unit tests (section 3).
5. Target "no fat tails / scan p99 < 0.5 ms per occasion" **NOT MET**: remaining p99 ~3.3 ms per occasion (2-3 passes per occasion,
   ~350-410 us per pass), remaining max ~10-14 ms. What is left is listed in section 6.

## 2. Profile: where an occasion spends its time

### 2.1 On air (`[MEASURED, DGX OTA, X410 34B2AF1, 2026-10-14, ab_T2a_1_091623, BTIM, ISAC_PDCCH_TIMING=1]`, per pass = one
`run_occasion_one`, 424 k passes in 150 s)

| stage | mean us / pass | share |
|---|---|---|
| post (Phase 2: lock wait + accept handling + PDSCH solver planning + UL discovery) | 236 | 49 % |
| decode (candidate polar decodes, all RNTIs) | 92 | 19 % |
| ulsweep (UL DCI length sweep, under `ul_length_lock`) | 65 | 14 % |
| fep_llr (FEP + chest + LLR) | 54 | 11 % |
| dlsweep / demap / prepass | 17 / 7 / 7 | 6 % |
| **TOTAL** | **479** (max 14 ms) | |

An occasion runs 1.8-2.2 passes (two verified banks + dwell / CORESET#0 / CSS0 passes), so ~1 ms per occasion with Phase 2 serialised
across the two consumers: that is the SCANTIME p50 of 0.5-1 ms (log2 bucket 1049 us) and the 2 consumers x 2000 occasions/s overload.
SCANPASS "bank mean 1220 us" counts a bank pass including its Phase-2 wait.

### 2.3 Answers to the brief's questions

- **FEP / fep_cache**: `[MEASURED, replay b]` fep_cache misses (18.9 k) = one per processed occasion (17.3 k) + a few: the cache
  already reuses FEP across every pass of a slot on the same thread; the 17 % hit rate is the pass mix, not a defect. The two
  consumers serve different slots, so there is nothing to share between them. FEP+LLR is ~50 us per pass. Not a lever.
- **llr_cache**: off in the OTA env; FEP is already cached, the LLR differs per CORESET extent. Not a lever.
- **Polar decode per candidate**: ~27 % of cycles; on Vodafone the dedicated CORESETs use pdcch-DMRS-ScramblingID != PCI, so the data
  scrambling depends on the RNTI and every (candidate, RNTI) pair is a genuine decode (no dedupe possible). Half of the attributed polar
  samples come from the UL length sweep (`ul_length_score`), the rest from the per-RNTI UL 0_1 and DL 1_1 tasks.
- **Bank pass**: the "bank" cost was mostly its Phase 2 (solver planning per accepted C-RNTI DCI), not its decodes.
- **Phase-2 lock**: it covers the PDSCH solver planning, DM-RS reading filter and the UL discovery init, i.e. 35-40 % of scan cycles
  plus the 200 ms one-offs. With N, `p2wait` (new BTIM bucket) is 13-23 us mean per pass.
- **Preemption / GPU waits**: not seen on the scan threads in the replay profiles (the PDCCH scan uses no GPU in this env;
  `pdcch_gpu` reference upload is off). On air the cores are shared with PDSCH consumer 0 (core 7) and the PUSCH consumer (core 6),
  both at lower FIFO priority than the scan threads (50) `[CODE-READ, P99-20261013 §4]`; not measured on air here.

N-R overlap is never below R-R: the differences are the run-to-run variance of a dropping, timing-dependent receiver (which occasions

bit-exactness of each change rests on section 3's unit tests and code reading.

## 6. What remains (not done here)

- **UL length sweep** under `ul_length_lock`: 60-120 us per pass (largest remaining stage on b), ~half of the polar decodes; it
  re-unscrambles each candidate per tested length (`ul_length_score`) and runs on every bank pass while any proven RNTI has no UL
  length. Levers: unscramble once per candidate per call (bit-exact); decode outside the lock. Not done: touches the sweep's evidence
  bookkeeping.
- **UL 0_1 tasks are not USS-hash gated** (`ussh_allows` gates DL 1_1 tasks only): per-RNTI UL decodes at every candidate (631 k UL
  decodes in a 12 s replay for 4.4 k UL accepts). Spec-legal only when 0_1 and 1_1 share the search space; would need an audit mode
  before use. Not done.
- **TDD UL slots on SIB1-less cells**: `[MEASURED, OTA ab_T2a_1_091623 ACCSLOT]` Vodafone (NSA, no TDD from SIB1) slots 8/9/18/19
  get ~18 k scan passes each and 0 CRC passes of any kind in 150 s (17 % of the scan passes); slots 7/17 (special) 6 and 13. A learned
  slot-direction gate would cut ~17 % of jobs but cannot be shown DCI-neutral quickly (special slots carry rare DCIs); TIM (SA) already
  skips them. Not done; candidate for the "TDD estimation from energy" gap (PROJECT_MEMORY K7).
- GPU polar (`NR_GPU_POLAR=1`, `sweep_gpu_prefill`) exists for the length sweeps but `nr_polar_sc_cuda_test` fails on this host
  (known ARM failure); not evaluated.
- Remaining occasion max 10-14 ms: not attributed (no profile was taken after change 4).
