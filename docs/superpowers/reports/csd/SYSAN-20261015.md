# SYSAN-20261015: whole-system analysis of DL/UL decode latency for one operator (branch csd/sysan, base csd/otatest 26d3028b5d)

Host: DGX GB10 (aarch64, 20 cores, CUDA sm_121, unified memory), X410 34B2AF1 over DPDK. Evidence labels follow PROJECT_MEMORY §0.1.
Cells are never pooled: `b` = Vodafone PCI 415 (`raw_pci415_12s_b`, 3680.01 MHz), `tim` = TIM PCI 923 (`raw_pci923_tim_12s_tile3`,
3759.99 MHz). Replays are `tests/passive_rx/p99_replay.sh` (air-like: sudo, FIFO-pinned OTA core map, SPEED=1, 4 RX), env
`rr-orchestration/ota/t26f.env` (frozen, unchanged) + `ISAC_E2E_TRACE=1`, one replay at a time under `heavy.lock`, private MPS dirs.
Replay load is about half of the daytime air load (earlier reports); every replay number is `[MEASURED, DGX replay <cap>]`.
"n = 3" means three interleaved replays per arm, grants pooled. No significance test was run; run-to-run spread is given.

## 0. Verdict

- **The oversubscription hypothesis: not supported in replay, partly confirmed on air.**
  - Replay: removing the PDSCH layout probes (`ISAC_PDSCH_SOLVER_PROBE_RATE=0`) or all recovery arms did not change the first decode
    pass of real grants (p50 547-622 vs 559-603 us). Queue waits are small (p50 7-8 us, p99 0.2-0.4 ms) and the cores are far from
    saturated. GPU discovery runs in its own SM partition: PDSCH kernels launched on an idle stream start within 53 us at p99.
  - Daytime OTA: the scan cores (68-83 %), the UL cores (67-73 %) and the producer core 5 (71 %, with the anonymous DCI solver
    floating onto it) are loaded with speculative work. 7-13 % of Vodafone DL grants wait > 500 us in the queue, and real UL grants
    wait p50 1.6 ms (section 9).
- **What limits 500 us is the cost of one pass plus the passes per grant.**
  1. **Per-pass floor.** A small-grant pass is about 110 us of GPU kernels and 200-300 us of serial host work between them: three
     host round trips (FEP -> chest -> demod -> LDPC), about 17 launches at ~5-7 us each, and CPU work in between. Burst p50: wall
     419 us, GPU kernels 232 us.
  2. **Large grants.** Above 96 PRB the first pass has p50 1.45-1.7 ms. The GPU kernels alone exceed 500 us (k_ldpc4 p99 394 us,
     k_delay_exact p99 284 us).
  3. **Recovery passes (Vodafone only).** On b, 58-62 % of real grants run more than one pass (1.75-1.8 passes per grant), and the
     retries take 36-43 % of the decode time. The S=0/S=1 toggle is the only arm that matters: 99 % of the rescues. On tim it is
     1.1 passes per grant and 6-10 % of the time.
  4. **One avoidable serial CPU step.** On slots that can carry an SSB (slots 0-3 and 10-13), PSS/SSS are FFTed on the CPU, 2 x 4
     antennas serially, before the GPU FEP. This adds 150-250 us at p50 and ~450 us at p90 to the first pass of ~40 % of grants.
     **Fixed by prototype S.**
- **Prototypes, all default off, bit-exact or loss-free by construction unless noted:**

  | prototype | first-pass p50 | whole-call p50 | CRC-OK | verdict |
  |---|---|---|---|---|
  | S `ISAC_SSB_FEP_GPU=1` | -8 to -20 % (replay); V on air with X: -20 % | b -5 %, tim -8 %; V on air (X) -20 % | unchanged | positive, recommended |
  | SB S + `ISAC_PDSCH_RETRY_BUDGET_US=1` (env only) | | b 1112 -> 872 us | 46.5 vs 46.7 % | recommended for the next OTA |
  | G `ISAC_PDSCH_RETRY_SNR_MIN_DB=3` | | b 1130 -> 830 us | loses ~1/3 of the S-toggle rescues | a CRC-for-latency knob, NOT recommended |
  | `ISAC_PDSCH_DMRS_ID2_ASYNC=1` | no change (expected) | | | frees ~20 % of PDSCH-consumer CPU after each decode |
  | `ISAC_UL_DISC_EVERY=8` | | | | UL latency effect not resolvable in replay: inconclusive |

  For SB, the S-toggle rescue lines fell from 9.9 to 7.3 % of grants while CRC-OK did not change; this is unexplained (see
  risks).
- **Sub-slot target, honest numbers.**
  - Best replay arm (S/X): CRC-OK grants on tim at whole-call p50 477-500 us, p99 1.1-1.3 ms; all grants p50 0.50-0.53 ms, p99 2.0-3.4 ms.
  - On b, whole-call p50 is 0.87-1.1 ms because of the S toggle.
  - Whole-call p99 < 500 us is **not reachable** with the current per-pass structure on this hardware (section 6).

- Not usable: an arm with nID GPU + CSI-RS discovery off (267 grants: discovery is needed).
- Removing probes or retries does not make the first pass faster (within spread). Speculation costs whole-call time on b only
  through the grant's own recovery passes (R0: p50 1115 -> 594 us), at a CRC price: R0 42.2 % vs 46.2 % on b.
- Never-decodable RNTIs are not the issue: 0-2 of 12-31 RNTIs, < 1 % of decode time. Failures are per grant.

  produced 609 plain-S CRC-OK and 193 toggled-S CRC-OK grants, and 6 of 30 (RNTI, tda) keys had both. A TDRA-keyed S predictor
  would not remove the toggle.

## 6. Limiting problems (ranked, with evidence)

1. **Per-pass host serialisation.** A small grant is ~110 us of GPU and ~330-420 us of wall. The three host syncs between FEP,
   chest, demod and LDPC, with CPU work and ~17 launches in between, set the floor (nsys timeline; burst analysis: 166 us p50 of
   non-kernel time per burst).
   - Fix: one fused or graph-captured chain per (grant shape), with chest pilots and allocation tables prepared during the FEP
     kernel instead of after it. Expected small-grant pass ~150-200 us `[INFERENCE]`.
2. **Large-grant compute.** For > 96 PRB, multi-CB LDPC at max iterations on CRC-failing CBs (k_ldpc4 p99 394 us, max 3.6 ms) plus
   the chest delay kernel (p99 284 us) exceed 500 us on 40 SMs.
   - Fix: early termination per CB (syndrome check), CB-parallel LDPC across the 40 SMs, and fewer SMs reserved for discovery when
     a large grant is in flight.
3. **Recovery passes on Vodafone** (1.75 passes per grant; the S toggle rescues ~10 % of grants, ~20 % of CRC-OK).
   - Fix: run the toggle as a second hypothesis in the same pass (shared FEP and chest; only demap and LDPC differ), or publish the
     first result and deliver the rescue late on a lower-priority stream (section 7).
4. **The SSB CPU pre-FEP** on 40 % of grants: fixed by prototype S.
5. **DCI latency before the decode starts** (slot -> enqueue p50 0.42 ms on tim and 0.8 ms on b; p99 1-2.7 ms). Even a zero-time
   decoder misses "slot + 500 us" end to end. b's anonymous DCIs go through a SCHED_OTHER async thread `[INFERENCE]`.
6. **UL.** In replay there is no layout lock, and 70-100 % of UL jobs are probe-ring layout-search work.
   - Per job wall p50 1.3-2.6 ms, p90 7.6-24 ms, CPU-bound (cpu ~ wall).
   - 68 % of UL CPU is the per-grant blind DM-RS-id scan (`nr_pusch_ul_disc_search`, 64 ids per grant), inline in every UL decode.
   - Real-grant UL latency needs a locked BWP and is measurable on air only.

## 7. Proposed architecture: protect the real-grant critical path

1. **Two lanes per resource.**
   - Critical lane: slot producer, PDCCH scan of known RNTIs, first decode pass of real grants.
   - Background lane: anonymous and USS discovery, nID and CSI-RS discovery, DM-RS id estimators, layout probes, recovery passes,
     UL discovery scans.
   - CPU: critical lane on big cores at FIFO, background on little cores 10-14 at SCHED_OTHER nice 19. Pin `pdcchJanon` off
     7-9 (today it floats on the PDSCH cores).
   - GPU: critical work in the RT green context at high stream priority; background in the discovery partition, which is already
     in place.
   - Already done: `DMRS_ID_ASYNC`, ID2_ASYNC (prototype), CHECK_ASYNC, UL GPU partition `rt`.
2. **Admission control with deadlines.**
   - Background work runs only when the critical-lane queues are empty: PDSCH backlog = 0 and no scan backlog.
   - A background job carries a deadline (sample lifetime) and is dropped when it expires; never preempt or delay a critical job.
   - Exists in part: `RETRY_YIELD` on backlog, `PROBE_LAST`, the GPU discovery budget 30 %.
3. **Recovery off the critical path.** Publish the first-pass result; queue the recovery arms (with their IQ snapshot, as the
   consumer already owns `g_owned_iq`) to a low-priority worker that may publish a late rescue. Combined with SB, b's whole call
   becomes the first pass: p50 0.5 ms.
4. **Launch fusion.** One CUDA graph per (stage chain, grant shape class): FEP -> chest -> demod -> LDPC with device-side
   dependencies, and no host sync until the LDPC CRC. Batch the grants of one slot group into one graph launch; the queue already
   groups same-slot grants. The CPU pilot generation and allocation tables are computed while the FEP kernel runs.
5. **Partition plan (one operator).**
   - Big cores 5 (producer), 6-7 (scan), 8, 9, 3, 4 (PDSCH, 4 consumers suffice: qwait p50 < 10 us).
   - UL on 0-1 (GPU FEP/LDPC in RT).
   - All discovery on 2 and 10-14.
   - GPU: 40 RT SMs plus 8 discovery SMs as today; make the discovery SM count dynamic (fewer while a > 96 PRB grant is in flight).
6. **UL.** Run the blind DM-RS id and timing scans in the background on a snapshot (or rate-limited with `ISAC_UL_DISC_EVERY`),
   so that a real UL grant runs only cached/DL-known hypotheses: target one FEP + chest + LDPC ~0.3-0.6 ms `[INFERENCE]`.

## 10. What is achievable on this hardware (one operator)

- **DL, with S + SB + the architecture of section 7 (graphs/fusion, recovery off the critical path)** `[INFERENCE from the
  measured components]`:
  - small/medium grants: one pass ~150-250 us (110 us GPU + ~50-100 us host);
  - whole-call p50 ~0.2-0.3 ms; p99 ~0.6-1.0 ms, set by > 96 PRB grants;
  - > 96 PRB p99 under 0.5 ms needs LDPC early termination and CB-parallel decoding (GPU work, same hardware).
- **Today, measured** (replay, best arm): p50 0.48-0.53 ms (tim), 0.87 ms (b); p99 2-3.4 ms. Daytime OTA (X): V whole-call
  p50 1.12 ms / p99 12.8 ms, CRC-OK grants p50 0.62 ms; T CRC-OK grants p50 0.50 ms / p99 3.8 ms.
- **On air the lanes of section 7 are a precondition**: the scan cores, the UL cores and core 5 are 68-83 % busy at daytime load
  (section 9). Without moving the speculative work off them, queueing adds a multi-ms tail on top of the per-pass floor.
- **UL**: one locked real grant should cost one FEP + chest + LDPC on the GPU, ~0.3-0.6 ms, once the blind discovery scans leave
  the per-grant path `[INFERENCE]`. Not measured: no lock in replay.
- **End to end (slot -> CRC)**: the DCI stage alone is 0.4-0.8 ms p50 today, so "slot + 500 us" also needs a faster known-RNTI
  scan.
- **What would need different hardware**: nothing for one operator at the measured loads. The GPU is 67 % busy, mostly discovery
  in its own partition; the cores are < 55 % busy.
  - Multi-operator simultaneous decoding (csd/mpci-int) multiplies the per-pass host work and the scan load. Its p99 at 500 us
    would need either the fused-graph design or a discrete GPU with a separate CPU host for discovery `[INFERENCE]`.

## 13. Risks

- **Replay is not air.**
  - Load is ~half of the daytime load; the producer is file I/O (`raw_iq_read`), not DPDK.
  - UL real grants never lock in the 12 s captures.
  - Discovery timing varies between runs (grants per run 1650-5900), and CRC-OK % per run on b spreads 37-62 %.
- **S** relies on GPU exact FEP equivalence; already validated for the main FEP with self-checks (`check_bad=0`). The SSB symbols
  are transformed twice on the GPU (pre-FEP and main FEP), so a few us of GPU time are added.
- **SB** drops the long-shot arms: 64 of ~5400 rescues in replay. The S-toggle rescue-count drop seen in m4 is unexplained.
- **ID2_ASYNC** shares the 8-deep dmrsIdBg queue: more drops can delay a DM-RS id decision.
- **UL_DISC_EVERY**: discovery of an unknown UL DM-RS id takes N times more grants.
- **E2E trace** adds one clock read per slot and per grant and lengthens EVMGRANT lines (parsers use non-anchored regexes;
  checked: `p99_stats.py`, `blindpipe_stats.py`, `mcs_tab.py`, `timpdsch_stats.py`, `antstats.py`).
- **Incident**: `rr-orchestration/ota/t26s.env` and `t26s.txt` (an obsolete 2026-10-11 env) were overwritten by mistake. The
  content is lost: rr-orchestration is not under git. `t26s.txt` now records this, and `t26s.env` was removed.
- Tooling: `agents_freeze.sh` matches any process whose cwd starts with an AGENT_WT prefix; `rr-csd-s` is in that list and is a
  prefix of `rr-csd-sysan`, so this branch's builds and sidecars are SIGSTOPped during OTA runs (seen; the profiling sidecars
  had to run from the scratchpad).
- A first OTA attempt failed at `load_lib` (the `oai_usrpdevif` module was not built in this build dir) before any radio
  streaming. One `agents_freeze.sh cont` I attempted while cleaning up was denied by the permission system. It was not needed: the
  starttest trap had already sent CONT, and no process was left stopped.
