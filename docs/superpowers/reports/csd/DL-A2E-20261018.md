# DL a2e: where the scan time before the enqueue goes, and what cuts it (2026-10-18)

Branch csd/int16-a2e (from csd/int16 698e1f5589). Host: DGX GB10, replay (tests/passive_rx/p99_replay.sh, TMO=90).
OFF = t26gE.env. All arms in this report also set `ISAC_A2E_TRACE=1` (diagnostic stamps, below) so the a2e split is
available in both arms. Captures are never pooled. b n_real is multi-modal (about 1.7-2.3k, 2.5-3.7k, 4.5-5.2k real
grants per run, whatever the arm), so b is also reported per mode.

## Answer

**Not ready. No t26aE.env was written; run t26gE on air.** The parse cache is bit-exact (0 mismatches live) but saves only
20-35 us per DCI, which p99 does not resolve; tim is slightly worse in the ON arm and one tim ON run lost 2/3 of its grants
for a reason not isolated (cache-only arm blocked by the heavy lock).

1. **The premise "the scan keeps running after the DCI is accepted and enqueues it later" does not hold.** A DL grant is
   enqueued by the same Phase-2 iteration that accepted its DCI, right after that DCI's own processing. Phase 2 reaches the
   candidate at once (Phase-2 start -> candidate: 0-1 us median). [MEASURED, DGX replay, b n=7 / tim n=4, OFF]
2. **a2e of a grant is three things** (medians; "tail" = grants with tot >= the run's p99):

   | part | b all | b tail | tim all | tim tail |
   |---|---|---|---|---|
   | slot arrival -> scan occasion start | 67-87 | 62-125 | 62-67 | 70-94 |
   | earlier passes of the same occasion (bank 1 waits for bank 0's whole pass) | 1-181 | 4-510 | 1 | 1-3 |
   | own pass: FEP, LLR, length sweeps, Phase-1 decode of every candidate | 185-226 | 189-286 | 147-150 | 163-171 |
   | accept -> enqueue (the DCI's own processing) | 180-190 | 65-245 | 110-112 | 140-156 |
   | of which the solver reading pass | 138-157 | 25-193 | 71-77 | 62-118 |

   [MEASURED, DGX replay, OFF arms of a2i/a2j/a2k/a2l/a2m/ab/ab3, b n=13 / tim n=7; ranges of per-run medians. The tail reading-pass low end (25) is a run whose tail is mostly grants without a solver pass]
   - **On b, bank-1 grants are the tail.** In the high-n_real mode b has two banked CORESETs. They run in order, so a
     grant of bank 1 waits for bank 0's full pass: 350-510 us in the tail, which is 29-39 of 35-47 tail grants.
   - **The solver reading pass is the "late enqueue".** Between accept and enqueue, the solver forms its readings by
     parsing every live DCI 1_1 layout: about 1250-1480 parses per DCI on b. The offset-key grouping that was meant to cut
     that to "a few dozen parses" is capped at 256 keys and the live set exceeds the cap.
     [MEASURED, DGX replay, b n=1, temporary per-parse counter, removed]
3. **No safe "enqueue before the readings" split exists.** The readings decide which jobs exist (full decode or probes,
   how many variants), their layout, allocation and so their rate matching, and the solver token. Enqueuing a job before
   them would decode with a guessed layout. [CODE-READ nr_pdcch_blind_monitor_rt.c, solver block before the enqueue]

## Rejected or not done

- **ISAC_PDCCH_PAR_BANKS=1 with the helper pinned to a free core (`ISAC_PDCCH_PAR_CORE=16,16`).** This is the existing way
  to stop bank 1 waiting for bank 0. Exploratory, not interleaved: b tail a2e 822-855 us against 990-1173 OFF, but p99
  3080/3110 against 2834-3495 OFF, so no visible p99 gain [MEASURED, DGX replay, b n=2 ON / n=3 OFF]. It also costs one
  core per scan consumer, and the OTA core map has no known free core (the replay used core 16, inside the heavy-job
  set). Earlier OTA (PDCCH-PARBANKS-OTA-20261016) with unpinned helpers was worse.
- **Raising the solver's 256-key cap.** That would cut the reading pass to one parse per distinct key, but members past
  the cap are then grouped instead of parsed one by one. That changes which layouts back each reading (solver evidence),
  the same kind of change that cost TIM n_real in RNTI-CACHE-20261017. Not bit-exact, not tried.
- **Pins before the RX fence.** Needs the PDSCH queue (and pdschRecov) started before the fence. Not done.

## Deviations and caveats

- Both arms ran with `ISAC_A2E_TRACE=1` (about 9 clock reads per pass plus one per candidate). The production env would
  not set it.
- The exploratory runs (a2i..a2p) used intermediate instrumented builds. Only the `ab`/`ab2` batches ran the committed code.
- My batch index `ab2.idx` collided with another agent's file of the same name in the shared scratchpad; my lines were
  moved to `ab3.idx` and theirs restored.
- p99 on b moves by ±400 us between runs of one arm. With n=6 a 30-60 us effect cannot be resolved.
