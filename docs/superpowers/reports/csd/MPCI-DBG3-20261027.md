## 2. Root causes and fixes

### RC1: a cell k>0 was never registered with the GPU decode pass [CODE-READ + REPLAY VERIFIED]
- `nr_dl_gpu_warmup()` (cell 0, runs once) is the only caller of `nr_gpu_pass_warmup()`.
- A8's per-cell prealloc hook `mpci_cell_prealloc()` never called it, although G3 §3 / G3b §5 say "per further cell, on that cell's bound thread, before the RX fence".
- So `nr_gpu_pass_dl_cell_ready(1)` was 0 and every cell-1 grant fell back with FB_CELL.
- Reproduced in the base replay: cell 1 had 0 pass grants of 38326, and `fallback[cell]=39502`.
- **Fix** (`executables/nr-uesoftmodem.c`): in `mpci_cell_prealloc`, for k>0 and only when `nr_gpu_pass_active()`, call `nr_gpu_pass_warmup(ue)`. The call runs bound to cell k, before the fence. It gives the cell its HARQ slab, its instance floor, its own FEP geometry when that differs (G3b), and the UL pass gate. A geometry the module cannot serve leaves the cell on the old path, with a log line.
- After the fix: `GPUPASS cell 1 registered: shared instances, graphs and shape classes of the first cell ...`, `fallback[cell]=0`, and cell 1 has 99.9 % pass grants.

### RC2: one cell's spurious FEP self-check mismatch switched the exact FEP, chest and pass off for every cell [MEASURED log correlation + CODE-READ + unit]
- `exact_run` (`nr_pdsch_gpu_exact.c`) compares the GPU FEP with a CPU reference. Both read the cell's live IQ ring, one after the other.
- When the producer overwrites the slot in between (a ring overrun or discontinuity, or a consumer lagging past the ring), the two reads see different samples and differ, although the GPU is bit-exact.
- The mismatch set the process-wide `g_on=0`. `nr_pdsch_gpu_exact_chest_entry()` then returned NULL, so `nr_pdsch_gpu_chest_pass_inputs` returned 2 and every pass of every cell was refused.
- The loop: CPU starvation, then a ring overrun, then the GPU off, then more CPU load.
- **Fix:** new pure header `openair1/PHY/NR_UE_TRANSPORT/nr_fep_selfcheck.h`. A mismatch counts only when it repeats on input that stays put: CPU reference A, GPU re-run of the same (antenna, symbol), CPU reference B.
  - A≠B, or the GPU re-run refused: void (the input moved).
  - A=B and GPU≠A: confirmed GPU fault. Same MISMATCH line and disable as before.
  - A=B and GPU=A: void (the first comparison raced the producer).
  - On void: `LOG_W ... self-check mismatch ... NOT confirmed` (the first 10, then every 1000th). The GPU FEP stays on, this slot gets the CPU FEP, and the decode's own lifetime check then discards stale samples as before.
  - The decision uses only the data, with no ring, slot or host knowledge.
- The chest and demod checks run on copies of their inputs, so they do not have this race [CODE-READ].
- Test `test_nr_fep_selfcheck` (6 cases): overwrite before the check → void; GPU fault on stable input → confirmed; input still moving → void; overwrite during the re-run → void; refused re-run → void; call order cpu/gpu/cpu. [OFFLINE VERIFIED] It failed before the header existed and passes now.
- Not reproduced in a replay: at SPEED 0.25 there were 0 `SHMIQ_OVERRUN` and 0 mismatches.

## 3. Core pool for N cells (task 2) [REPLAY VERIFIED CORE_PLAN line, same layout code as the OTA; radio=1, shm_iq counts as a radio]
Host: isolated 15-19, DPDK 17-19, uhd 15, ring 16. General CPUs 0-14 (A725: 0-4 and 10-14; X925: 5-9).

| cells | RT readers / feed | W | mode | lane / hk | pool |
|---|---|---|---|---|---|
| 1 | 5 / - | 14 | SEP | 5 / 3 | 6 (6,7,8,9,3,4): 4 fast + 2 little |
| 2 | 5,6 / feed 7 | 12 | COMPACT | 4 (11-14) / 1 (0) | 7 (8,9,1,2,3,4,10): 2 fast + 5 little; `max_cells=11` |

- **Derivation:** W = general CPUs minus the readers. Pool = W − lane − hk.
- **Verdict:** the pool did not shrink from 1 to 2 cells (6 → 7), so the R3 rule (pool and lane shared, one RT reader per cell) holds. **No layout change made.**
- **What did shrink:**
  - Fast-core share: the cell readers and the feed reader take the fast cores 5/6/7.
  - Usable tokens: with the GPU channelizer (OTA), CHAN reserves the fastest token, leaving 6 decode/scan tokens for 2 cells.
  - Beyond 2 cells [CODE-READ, not measured]: each extra reader removes one CPU from W, so the pool goes down by about one per cell. `max_cells=11` admits cells down to a 2-token pool.
- **Open item (B3/B2 owners):** admission should weigh the cells' decode demand against the pool, not only "readers distinct and pool ≥ 2".
- With RC1/RC2 fixed, the 2-cell replay's decode waits are about the same as the base 2-cell run (waited 78663 of 661585 jobs, p99 ≤ 2048 us; base 76558 of 575974). The solo controls wait less (decode wait p99 ≤ 512 us / ≤ 64 us).
