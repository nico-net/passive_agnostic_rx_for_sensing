## 1. DL HARQ soft combining inside the pass

### Design
- The soft sum of a failed TB (the CPU path's `d`, int16, N = 66 Z or 50 Z entries per code block) lives in **device HARQ blocks**: a pool of `NR_GPU_HQ_BLK` = 2048 blocks of 66 * 384 int16
  (104 MB, allocated in `nr_gpu_pass_init`, before the RX fence; counted against the pass's VRAM). Each of the 64 entries of the existing LRU store (`g_harqc`) holds `hb` (the blocks of its TB, one per code block)
  while its sum is on the device (`on_gpu`). Pool and eviction: `nr_gpu_pass_hq.h` (`nr_hq_pool_*`, unit tested); an entry that needs blocks and finds the pool short takes them from the least recently used idle entry
  (that sum is dropped, counted `dev_blocks evict=` in the HARQC line; `nospace=` counts grants decoded without keeping their sum).
- `k_rdm` (rate dematching, `nr_gpu_pass_post.cuh`) takes `hq_mode` / `hq` per code block: 0 none; 1 first transmission (clear = 1: the int16 sum is stored, the whole N written); 2 retransmission (clear = 0: the stored sum is added to,
  int16 wrap as `d[ind] += soft`, then stored). The int8 LDPC input is the saturated sum, exactly what `prep_segment` hands the CPU decoder. Combined and stored in one kernel, in graph: no new node, no host round trip.
- Host decision = the CPU path's decision, same function (`harq_retx_decide`: same NDI on the process, rv != 0 or rv 0 admitted by the census, TBS kept from the first transmission). The pass block of
  `passive_decode_body_core` acquires the entry (`harqc_acquire`), decides, arranges the blocks (uploads a sum an earlier CPU decode left on the host), runs the pass, and commits what `passive_ldpc_decode` would leave
  (ndi, tbs, soft_valid = !tb_ok, counters g_hq_first / g_hq_retx_try / g_hq_retx_ok, t_last_hq_retx). A decoded TB returns its blocks to the pool. The CPU path, when it needs a sum that is on the device (a fallback
  between the two decoders), downloads it (`nr_gpu_pass_hq_down`), then owns it.
- What stays on the old path: SI soft combining (`ISAC_SI_SOFTCOMBINE`, deferred / off in the frozen config; gate `harq`), probes (HARQ-neutral by construction).
- Consequences handled: a pass that returns `need_cpu` invalidates the entry (the device sum already holds the grant, the old path decodes from scratch); the sampled shadow decode is not taken for a combining
  retransmission (the old path would see the sum the pass has already stored), and a shadowed first transmission leaves the entry invalid so the old path decodes it fresh; the in-graph no-chance gate skips before the
  rate dematching, so a skipped grant stores nothing (as the CPU path).

### Why a real grant with combining on takes the pass [code reading + unit test]
- `passive_decode_body_core`: the former gate `gp_hq_arms(rnti) ? NR_GPU_PASS_GATE_HARQ` is now `gp_hq_si(rnti)` = `nr_gpu_pass_hq_refuses(hq_armed, is_si)` = armed AND SIB1/SI soft combining. For a C-RNTI grant it is false, so no gate refuses it
  because of HARQ; the rest of the gate chain is unchanged.
- Unit tests [unit test, DGX GB10]: `GpuPassHarq.OnlySoftCombiningOfSiStaysOffThePass` (the gate function); `GpuPassHarq.CombinedRetransmissionDecodesWhatNeitherDecodesAlone` (whole pass: a first transmission with mode 1 and a
  retransmission with mode 2 both return rc 0, i.e. are taken by the pass; 33 failed first transmissions over SNR 7 .. -1 dB, 48 PRB, 2 layers, 64QAM: the retransmission alone decodes 3, the combination 17, 14 only combined,
  every combined TB equals the transmitted one, combining never loses a TB the retransmission decodes alone).

### Equality with the CPU combine [unit test, DGX GB10]
- `GpuPassPost.RateDematchHarqCombineMatchesCpu`: 600 random parameter sets (BG 1/2, 14 lifting sizes, filler, LBRM on a third, repetition up to 2 N, rv 0..3 per transmission, 2-3 transmissions, full-range LLRs that wrap int16,
  a dirty device slot and a dirty CPU buffer before the clear): 1733 combined transmissions, the int8 LDPC input AND the stored int16 sum bit-equal to `nr_rate_matching_ldpc_rx` with `d_to_be_cleared` = 1 then 0
  (the CPU combining code), 426 LBRM segments, 10.8 M saturated inputs. Bit-equal inputs to the bit-exact LDPC give the same CRC verdict; the LLR tolerance is zero.
- `GpuPassHarq.BlockCopiesRoundTrip` (host layout <-> scattered device blocks, the fallback path), `GpuPassHarq.BlockPoolHandsOutKeepsAndEvictsWithoutLeaks` (no block lost or given twice; LRU order; a refusal leaves the entry empty).

Reading:
- DL alone does not depend on the SM count above 32 (32 -> 40 SMs: 0 .. 6 %; the whole 48: up to 13 % at 17 blocks); 24 SMs cost +20 %; the 16-SM layout (DL 16 / UL 24) failed an assertion of the bench (not investigated, unusable as is). The SM cut is NOT what
  separates the 531-543 us of the frozen build from the 606-668 us of the A+D build: with the UL idle the DL span is the same on 32 and on 40 SMs.
- The old split pays on the UL: 8 SMs give 376 us (106 PRB) and 571 us (217 PRB, already over 0.5 ms alone); with UL on all RT SMs: 285 / 353 us.
- Under saturating UL load the old split keeps the DL p50 lowest (314 vs 375) but has the worst DL p99 (1029 vs 783 .. 481); "one ctx" is excluded by the UL median (845 under DL load); DL24/UL16 is the only layout whose UL
  median stays under 0.5 ms even under saturating DL load for 217 PRB (432 us) but it costs the DL +20 % always.
- Chosen: **final** = UL borrows the DL SMs (dynamic split by green contexts with overlapping SM sets and stream priority: DL highest, UL / probes lowest), probes confined to the 8-SM group so that a probe never occupies a DL SM.
  Feasible on sm_121: the driver accepts overlapping descriptors, three contexts (DL 32, UL 40, probes 8) run. DL alone is unchanged, DL p99 under load is 7 .. 24 % lower than the old split, the UL median alone drops by 24 % (106 PRB) and 38 %
  (217 PRB) and stays under 0.5 ms with 106 PRB DL load; with 217 PRB UL against two saturating DL loops it reads 541 us (the price of not reserving SMs for UL; DL24/UL16 would read 432 us at +20 % DL span).
  DL p50 under load is +19 % vs the old split (375 vs 314 for 1 block).
- sm_89: the RT partition is 26 SMs (34 - 8 discovery) < 32, so there is no DL / UL split there at all (one RT context, priority only); the new layout changes nothing on that device. NOT measured.
- Not measured: a real mix on air (DL and UL passes at their real arrival rates); only these saturating loops. The DL p99 improvement is a bench figure from 400 samples per cell.

## 5. Not done / risks
- On-air: nothing measured. The host glue of the HARQ entry (acquire / decide / upload / commit / shadow) is exercised only by code reading and by the pieces it calls; the pass-level behaviour by the whole-pass test above. A first on-air
  run should read the HARQC line (`first`, `retx_combined`, `dev_blocks evict / nospace`) and the new census (`tbparam_why[...]`, `gate[... gw_ready llr_ovr cap force_cpu]`).
- GrantWork owner (publishes un-normalised LLRs) and READY decodes stay on the old path (see the table); the pass would need a pre-normalisation copy of the LLRs for the owner. If the census shows `gw` large, that is the next change.
- The retransmission is never shadow-checked against the old path (it would see the stored sum); a first transmission is, when the sampled shadow is on (it is off in the product, `G.check = 0`).
- VRAM: +104 MB HARQ blocks, +190 MB LDPC pass contexts, +450 MB graphs (1477 -> 1924 MB) on the GB10; on the 8 GB card the cap stays 2048 MB, the same set would stop warming near the end (segmented classes with the widest shapes and the 4-DM-RS classes
  last; counted as unseen). Not run on sm_89.
- Segmented grants of 129 .. 137 segments and segmented classes with 1 or 4 DM-RS symbols remain off the pass (counted).
- The DL / UL layout change (UL overlapping the DL SMs) is a bench decision on synthetic saturating loads; on air the DL p50 under concurrent UL load is expected ~20 % higher and the DL p99 and the UL median lower; to be confirmed.
