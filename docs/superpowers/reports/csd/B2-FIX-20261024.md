### The OTA pair is not an A/B of the code [MEASURED, DGX OTA 2026-10-24 ota_runs/ab_bVC_1_041316 vs ab_bVB_1_041848, n=1 each]

DCIs seen 7599 vs 2470, EVMGRANT 6988 vs 2140. One UE per RNTI needs hundreds of grants to solve; the heavy UEs were absent five minutes later [INFERRED traffic, the RNTI sets are MEASURED].
- Additionally the second dedicated CORESET (nID 52648, the one carrying 0x190) was found by the main run's GPU nID stage at pass 140 and banked; in the batch2 run the stage published only nID 32328 for all 328 passes. With no heavy UE in the cell there was nothing for it to find [INFERRED].
- Same class of mechanism as the replay bimodality below. A decisive OTA check needs a repeat of the same arms back to back and the RNTI/DCI totals reported next to solved.

### The bimodal low outlier (also on main) [MEASURED, DGX replay V]
Low runs decode ~5000 grants instead of ~10000 and see 19-34 RNTIs instead of 40. Every low run banked ONE dedicated CORESET until late in the replay (second `bank add` at log line 38k-44k of 42-48k) while high runs banked both (nID 10163 and 62922) within the first 5000 lines. Final `bank=` is 1 in low runs, 2-3 in high runs.
Cause [MEASURED + CODE-READ nr_pdcch_blind_monitor.c, discovered queue]: the GPU nID stage publishes its list in an order that depends on the capture window it sampled. When the list starts 62922, 9020, ... the wrong nID 9020 (strong spurious ID) is dwelt as cover, as interleaved cover and as raw lines, each rejected only after NR_PDCCH_EXTENT_VERIFY_OCC = 4000 occasions, and every list refresh re-queues it from the start (cap3 log: 9020 rejected 4 times: 2/7, 6/7, 7/7, again 2/19) before 10163 is reached. The run then benefits from the second CORESET only in its last seconds. Pre-existing nondeterminism, not caused by batch2.

### Fix: REJECTLAST (nr_pdcch_blind_monitor.c, no flag, no cell constant)
An nID whose dwell was rejected this epoch is tried again only after every queued nID that has not failed yet (rejected nID kept last, still retried). Pure ordering of the discovered-CORESET queue; the rejection memory dies with the epoch reset.
Unit test: DiscoveredCoresets.RejectedNidIsRetriedAfterUntriedOnes (test_nr_pdcch_blind_monitor, all DiscoveredCoresets tests pass).
Replay after the fix [MEASURED, DGX replay V, 8 reps, same recipe]: solved=1 lines 196, 199, 206, 198, 179, 213, 211, 114; decoded 8.9-10.9 k. 0 of 8 low runs (baseline 6/21 = 29 %; chance of 0/8 at that rate about 6 %, so this is supportive, not proof). Rep 8 (114) is a mid run like b2 rep3 (123), not the 33-71 mode. Not yet a gate-grade result; the OTA check below is the real one.

## 2. Problem 2: SIGSEGV in nr_scan_ssb on a weak or absent cell (PCI 675, OTA 04:35)
Cause [CODE-READ + disassembly of the crashing binary, MEASURED symbol nr_search_ssb_common+0x70c = nr_initial_sync.c:250]: the acquisition FEP diagnostic in do_time_to_freq() (static counter s_fepdiag_acq_left = 40, i.e. only the first 40 acquisition SSB candidates of a process) reads rxd[rx_offset - nb_prefix_samples + i] with unsigned 32-bit index arithmetic. With the PSS peak at pos == nb_prefix_samples (72 at N=1024; the pinned-target path accepts any peak, a weak cell puts the peak anywhere) sample_offset is 0 and rx_offset - cp = 63 - 72 wraps to 2^32 - 9: a read 16 GB away. The fault address 0xec153c000b1c is a heap-arena base plus a small offset, consistent with that wrapped index [INFERRED from the address]. Not a PSS_ACC bug: the fold buffers are sized by `period` and indexed modulo it.
Main has the identical code (introduced 0fc4f214ae, present in 42e58776d8) [CODE-READ]; it is a latent crash on main too, hit only when a weak-cell peak lands in [cp, cp + cp/8) within the first 40 candidates. The narrow51 build at 03:00 was fine because the cell was stronger (peak far from the start).
Fix (commit "fix(sync): acquisition FEP diagnostic ..."): new nr_iq_mag_stats() in nr_pss_decim.c/.h computes the sums over [start, start+n) clipped to [0, xlen); the diagnostic uses it with 64-bit start. Test: test_nr_pss_decim PssDecim.IqMagStatsNeverReadsOutsideBuffer (buffer between PROT_NONE guard pages: windows before, after and outside; the exact failing arithmetic). All 5 tests of test_nr_pss_decim pass. No offline reproduction of the crash itself (needs a peak at exactly one CP); the unit test reproduces the arithmetic.
