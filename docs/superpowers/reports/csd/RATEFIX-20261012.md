## 1. Diagnosis (why STABLE is rare)
[OTA-log] RATELIMIT lines per 150 s run: VB1/Vz1/Vz2 none beyond cfg; VB2 STABLE(75799) -> SEARCH new-pattern(77724) -> STABLE(214839) -> SEARCH epoch; Tz1 STABLE(27719) and stays; Tz2 STABLE(22119) -> new-pattern(38593) -> STABLE(93292) -> crc-drop(107528). No `confirmed-lost` over the air.
Three separate mechanisms:
1. **Vodafone never settles by design of the criterion** [OTA-log]: VB1 logs 126 `CSIRS_BLIND CONFIRMED` lines spread to the end of the run (46 confirmed in VB2), i.e. the set keeps growing; STABLE needs the set unchanged for max(2 cycles, 2x build time, 4 x slowest period). This is correct behaviour, not a bookkeeping bug; I did NOT loosen it (a premature STABLE would delay late confirmations, and time-to-confirm must stay unchanged). Added a `RATELIMIT WAIT n_conf lost since_change need` line every 30 s of stream time so the blocker is visible next run.
2. **Exact-hypothesis match -> spurious `confirmed-lost`** [replay-log, confirmed by the CSIRSRATE warning]: tim 12 s replays RL1 and P21: hypothesis `rb=0:208` is admitted, STABLE reached at slot ~27.4k, then blind_rt widens the resource to `rb=0:217` (and an offset 16/17 pair) and the exact compare fails: `SEARCH reason=confirmed-lost` ~0.5-4.6k slots after STABLE, followed by a re-burst of the acquisition window (rearm) and `CONFIRMED #0 after 1449 slots` re-confirmation. n_conf=4 for 2 real resources (208 and 217 hypotheses both counted) is the same bookkeeping issue.
3. **Single-look escalations** [OTA-log, replay-log]: `new-pattern` fires 120 slots after STABLE (replay P23) and 1.9-16 k slots after (VB2, Tz2); the learned baseline compares offset exactly (TRS pair 16/17 looks new) and one noisy footprint suffices. `crc-drop` is a 3-sigma test re-evaluated on every disjoint 200-decode block with sd -> 1e-9 at p0 near 0/1 and sensitive to low baseline (Tz2 p0=0.083, ~200 decodes): repeated looks guarantee false alarms over a long STABLE.

## 2. Fix (default-off flag unchanged; flag-off path untouched)
* `nr_csirs_blind_rt_discovery_match()` (nr_csirs_blind_rt.c/.h, read-only helper, 25 lines): index of the confirmed NZP resource that is the same physical resource: same first symbol, density, period, an offset phase, RB spans overlapping >= half of the narrower, same row => freq_domain overlap. Tolerates widening/merging. `discovery_confirmed()` (used for the sweep skip filter) is unchanged.
* `rl_update`: n_conf = number of DISTINCT matched confirmed resources (bitmask of match indices; two hypotheses of one resource count once); `lost` is now a level (edge only in SEARCH); known-footprint baseline compares offsets within +-1 slot cyclic (TRS pair); `new_pattern` requires the same new footprint in two consecutive observations (noise footprints do not recur).
* State machine (nr_csirs_disc_rate_internal.h): `confirmed-lost` needs 2 consecutive unmatched observations; `crc-drop` uses a two-proportion z with +1/+1 pseudo-counts (valid at p0 = 0 or 1), still 3 sigma, and needs 2 consecutive violating blocks, blocks always advance. Statistical debounce, no per-cell constants. New `need` field + WAIT log.
* Unit tests updated/added (nr_csirs_disc_rate_test.cc): lost debounce (consecutive vs not), CRC two-block rule, recovery resets the streak, extreme baseline p0 = 1. NOT RUN.

## 3. Extra normalize kernels (43 RL vs 2 base) [CODE-READ, INF]
The RL arm of GPUALLOC differed from base in two flags (RATELIMIT and NORM_COALESCE; base had both 0). With the rate limit alone no burst can occur unless STABLE was reached and then escalated (rearm only on STABLE->SEARCH). DECTAIL's own nsys base showed 98 normalize-attributed kernels (3023 ms) with COALESCE=0, GPUALLOC base 2, RL 43, P2 0: the count varies 0..98 between single nsys runs of near-identical configs, so it is dominated by when the acquisition burst/ingest windows land relative to RT work, not by the rate limit. The one real RL contribution is the spurious `confirmed-lost`/`new-pattern` -> rearm of a 2.56 s burst after STABLE seen in the tim replays above (mechanisms 2 and 3), which this fix removes. Not verified by nsys; to confirm, count RATELIMIT SEARCH lines vs normalize kernels in the same run.
