## What was built
- `radio/COMMON/shm_iq_chan_gpu.{cu,h}` + `shm_iq_chan_kern.h` (T0 import, plus `ck_mix_ab`): `iq_chan_backend_t "gpu"`, module `libshm_iq_chan_gpu.so`
  (dlopen'd; the receiver keeps no CUDA link dependency). Kernels: fused mixer + first halfband stage (as MPCIFIX ABI 2), **8 outputs per thread**
  (1 output/thread spent most of its time in CTA set-up and the barrier: 3-6x faster), last stage writes sc16 directly, history kernels read-before-write in
  one CTA so any block length works, partial 4096-phasor blocks follow iq_ddc. SHARED: **zero copy** (kernels read the wideband ring in place, write the cell
  buffers); DISCRETE: pinned staging + H2D/D2H. Polled waits (cudaEventQuery, 20 us sleeps after 0.1 ms). No allocation after the RX fence. GPU ledger
  module `chan` (GPUMEM), GPU budget module `NR_GPU_MEM_CHAN` (weight 0, committed bytes, admitted iff committed total + bytes <= B; absent from the
  GPU_MEM line until used, so N=1 lines are unchanged). Core pool: CHAN lease around the CPU side of a run (never across the GPU wait), demand 1.
  Diagnostic `IQ_CHAN_GPU_SLOW` (run > 50 ms, launch vs wait). Catch-up batching: up to 16 waiting blocks per run (in place), output identical.
- `radio/COMMON/iq_chan_gpu_sel.c` (in mpci_iq): the **CHAN path** of `nr_gpu_path` (`NR_GPU_PATH_CHAN`): module next to libnr_gpu_platform (dladdr),
  self-check vs iq_ddc on the load's geometry (<= 1 LSB, <= 1/1000 differing), budget fit; SHARED -> gpu (`reason=shared`), DISCRETE -> bench trial (GPU vs one
  CPU thread per block; forced-DISCRETE on GB10: gpu 136 us vs cpu 564 us -> gpu), CPU tier / no module / failed check -> cpu. One decision per process.
  Line `SENSING: IQ_CHAN_GPU gpu_ok=.. selfcheck_max_lsb=.. selfcheck_differing=.. bytes=.. headroom_mb=.. tier=.. placement=.. choice=..`.
  Without the platform library in the process (pure-CPU unit tests) nothing changes.
- Platform registration: `nr_gpu_path.{c,h}` (CHAN), `nr_gpu_memstat.{c,h}` (NR_MS_CHAN), `nr_gpu_membudget.h` (NR_GPU_MEM_CHAN, weight 0),
  `nr_gpu_platform.c` (format skips an unused weight-0 module; the two "every module but the graph" loops now skip GRAPH explicitly instead of relying on
  it being last: same result).
- `iq_chan.c/h` edits (registration/selection and the step's input path only; CPU worker/lease code of CHANPOOL untouched): selection through
  `iq_chan_path_select` when no selector is set (iq_chan.c ~384-392); CPU fallback when a selected backend cannot be created (~471-475); `ring_direct` /
  `ring_still_valid` helpers (~734-754); `iq_chan_step` in-place input + catch-up batch (~777-805); `batch` field, geom.block = block x batch, obuf / narrow
  ring sized for the batch (create, cell_add). `iq_chan.h`: optional members `direct_in`, `max_batch`. `iq_feed.c`: MPCI_FEED gains
  `chan_gap_max_ms= chan_work_max_ms=` (multi-cell only).
- Bed: `tests/passive_rx/mpci/g5_make_wideband.py` (synthetic wideband capture from single-cell captures), `g5_fast_pub.c` (real-time file publisher; the
  existing mpci_file_pub reaches only ~0.23x real time at 245.76 MS/s x 4), `g5_wide_replay.sh` (arms gpu / cpu / ctl). `cmake_targets/mpci_gpu.cmake` `# ---- G5 ----`.
- Statics table rows (PROCESS, G5); `static_audit.py --check` passes.

NO FLAGS: no new env var / option / -D. Note: registering the CHAN path in the existing per-path layer makes the existing family `NR_GPU_PATH_<NAME>`
also accept `NR_GPU_PATH_CHAN=cpu|gpu` (used only for the bench's cpu arm, not by default).

Readings `[REPLAY VERIFIED ...]` unless labelled:
- The overruns are throughput shortfalls, not stalls: worst step gap 13-31 ms and no run above 50 ms (`IQ_CHAN_GPU_SLOW` count 0) in the instrumented runs,
  while the lag grows to the full 1.09 s ring. Under the decode load the per-block cost (6-8 small launches + one wait per 0.27 ms block) is far above
  the idle 0.17 ms per ms. [HYPOTHESIS] Fewer, larger runs fix it: the catch-up batching (HEAD) does exactly that when behind; not yet measured.
- Cell rings: the cells' own consumers also overrun their 100 ms narrow rings (SHM_IQ_RING_NARROW_TARGET_MS, G6) at start-up and after a channelizer
  skip, while the control's cell rings are 1 s deep; one such resync moved cell 0 onto co-channel PCI 380 in gpu(a)_1. Part of the p99/CRC gap is this
  ring depth, not the channelizer (open item 3).
- The earlier rounds with mpci_file_pub ran at only ~0.23x real time (37.6 G samples in 600 s): those (g5ctl_1_144928, g5gpuA_1_145945) had 0 overruns
  but are not real-time evidence.
- CPU backend at 245.76 MS/s x 4 x 2 cells is not sustainable on this host (idle 0.63x on one thread; OTA 10-27: 147-153 overruns/300 s with 7 threads),
  so the control is the pre-channelized one (B.6 criterion).
