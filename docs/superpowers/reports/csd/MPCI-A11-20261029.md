# MPCI-A11 — PDSCH recovery worker per cell (2026-10-29)

Branch `mpci/c-a11` off `mpci-main` 51c8f013ab. Labels per PROJECT_MEMORY §0.1. Host: DGX GB10 aarch64 (shared with another user; builds and unit tests only, no replay, no radio).

## Problem
`[c1] RECOV worker FAILED to start` in 8/8 two-cell OTA runs [MEASURED, DGX+X410 34B2AF1, 2026-10-26..28, DL-HEALTH-20261029 §3]. With `g_recov_ok` false the decoder runs in recovery mode 0 and
`RETRY_ARMS_OK() = nr_hq_retry_lane(true, 0)` is false (HARQ combining is always on), so no TDRA/CDM/CSI/wide-MRC retry arm and no late recovery ever ran for a cell > 0; Vodafone as c1 crc_q 68-70 % vs 85-95 %.

## Root cause analysis
What the evidence fixes [CODE-READ + OFFLINE VERIFIED, unit]:
1. `nr_pdsch_recovery_start` returns -1 only from two places: a heap allocation (queue, free list, job slots) or `pthread_create`. Neither logged a step or errno.
2. The module is correct per cell in isolation: the A5 interleave test and a new test start cell 1 late from its own thread (after cell 0 runs) and it works; per-cell statics, the PI mutex init and the restart path are fine. So it is not a singleton guard or missing per-cell state.
3. The discriminator is WHEN cell 1 starts. Cell 0's queue (and so its worker) starts in `nr_dl_gpu_warmup`, before the RX fence and `mlockall(MCL_CURRENT|MCL_FUTURE)`. Cell k > 0's queue is started lazily from the monitor's first occasion on the cell's own thread [MEASURED, sw28_R1_1_091747/run.log: c0 `RECOV worker started` line 336, `HOST_MEM mlock done flags=CURRENT|FUTURE vmlck_mb=130531` line 384, `[c1] RECOV worker FAILED` line 1014]: after the fence, after the process locked ~all host memory, from a thread that may hold a core-pool lease. The worker's arrays and its stack are the only allocations of that start that were not made earlier; the 8 snapshot holders of the same call succeeded.
4. Real per-cell defects found on the way (all fixed): the worker leased its core with `nr_pool_site_acquire(NR_POOL_RETRY, 0, 0)` (cell 0's fair share for every cell); the raw `pthread_create` was not `nr_cell_thread_create`, did not use `nr_pool_site_home_attr` (a lessee's single core was inherited), and the result of `pthread_setaffinity_np` was ignored.
5. NOT proven from the logs: which of alloc/pthread_create failed (the line did not say). The fix removes the late path and the next OTA line names the step if it ever fails again.

## Fix (no flags, no new env/option/-D)
- `nr_pdsch_recovery.c`: worker lifecycle split. `nr_pdsch_recovery_prepare(job_bytes)` builds the arrays and creates the worker thread parked (own plain mutex/cond for the arm hand-off, so the wake never takes the PI mutex); `nr_pdsch_recovery_start` only arms (or builds, for a late/test start). Thread via `nr_cell_thread_create` + `nr_pool_site_home_attr`; the armed worker places itself (`sched_setaffinity`, a refusal is logged and it falls back to nice 10); RETRY lease for the worker's own cell. Every failing step records `step=<what> errno=<n> (<text>)` (`nr_pdsch_recovery_last_error`).
- `nr_pdsch_passive_queue.c`: `nr_pdsch_passive_queue_cell_prealloc` (called per admitted cell, including the A12 spare slot, before `nr_cell_alloc_fence`/mlock) calls `nr_pdsch_recovery_prepare`; the queue start arms it. The `FAILED to start` line is kept (grep) and followed by `RECOV worker start failed: step=... errno=...`.
- Fallback: if no worker can start, the cell runs the arms inline on its consumers (`g_recov_inline`, own slots, at most 2 jobs per slot group, `nr_pdsch_recovery_run_inline` = the worker's job body with no wait for first-pass work: it yields when some waits, held-back feedback delivered once). Logged once: `RECOV worker unavailable: the retry/recovery arms run inline ...`. If even that cannot be set up: `arms are OFF for this cell` (error). N=1 with a working worker: same lines, same behaviour.
- `nr_pdsch_passive_queue_recov_state()` (0 none / 1 worker / 2 inline) for tests.
- `tools/mpci/mpci_statics.tsv`: 10 new rows classified PER_CELL; `static_audit.py --write` then `--check` rc 0.
