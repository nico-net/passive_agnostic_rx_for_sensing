# MPCI-DBG2: no C-RNTI decoding with two cells in one process, and the exit crash (2026-10-26/27)

Branch `mpci/c-dbg2` (from mpci-main 86a3f902e2, ff to 1197a835ad, merged mpci-main de2f881872 for G3b). Host DGX GB10 aarch64, shared.
Replays: `tests/passive_rx/mpci/run_two_cell_replay.sh`, raw captures (Vodafone PCI 415 12 s, Iliad PCI 403 4 s), SPEED=0.25, file publisher, shm_iq device, no radio.
Labels: [REPLAY VERIFIED, DGX GB10, file replay] = a replay run here; [OFFLINE VERIFIED, DGX GB10 aarch64 unit]; [CODE-READ].
Counts are taken from run.log with ANSI stripped, per `[cK]` tag (solo logs: untagged = cell 0); C-RNTI = EVMGRANT lines with rnti != 0xffff; CRC ok = `crc=1`.

## 1. Facts first (log diff, 2-cell vs solo, base build) [REPLAY VERIFIED]
- Cell 0 in the 2-cell run never printed `CSIRS_BLIND CONFIRMED` (solo: 32), never `ACQ carrier CONFIRMED` (solo: 1), `CORESET_DISC state=SEARCHING reason=carrier_pending nid_passes=0` for both cells, 0 `PDCCH_NID_GPU pass` (solo: 272), 0 `discovered CORESET` / bank adds. The C-RNTI chain in this receiver is: CSI-RS confirmed -> carrier (Point A) verified -> nID GPU sweep armed -> dedicated CORESET banked -> C-RNTI DCI 1_1 / 0_1 length lock. It broke at the first link.
- `CSIRS_DISC worker could not start; slot discovery feed disabled` printed once, during cell 1's per-cell prealloc.
- shm_iq input is not the cause: SHMIQ_END dropped_in equals the capture-loop discontinuities (cell 0: 4 x 61374, cell 1: 14 x ~46416), 0 overruns.

## 2. Root causes, evidence, fixes

### RC1 CSI-RS search / confirm queue / monitor bank were process-wide [CODE-READ + REPLAY VERIFIED + unit]
`nr_csirs_blind_rt.c` (+ `nr_csirs_disc_confirm_internal.h`) and `nr_csirs_monitor.c` were not in the audit globs (`nr_csirs_disc*.c` only) and never converted. Cell 1's `nr_csirs_disc_pipeline_init` called `nr_csirs_blind_rt_discovery_prepare(51-PRB grid)`, which returned -1 because the single queue was prepared for cell 0's grid; the pipeline then called `nr_csirs_blind_rt_discovery_disable()`, which set the process-wide `discovery_disabled`: every later enqueue of cell 0 was dropped -> no confirmation -> carrier never verified. The monitor bank was shared too: cell 0's confirmed resources (RBs 128..179) became due on cell 1's 51-PRB slot thread -> `nr_ue_csi_rs_sensing_capture_shifted` out of the grid (H1 experiment: SIGSEGV in `hashtable_get`/`gold_cache` from a DL actor with an IQ-valued address).
- Experiment H1 (throwaway, not committed: skip the disable for cell != 0): cell 0 CSI-RS confirmed 3 and carrier confirmed in 120 s, then the crash above -> both halves of RC1 confirmed.
- Fix (664e9cdf57): declaration-only `NR_CELL_STATIC` conversion of all mutable state of the three files; the >64 KiB objects that only the discovery path reaches (frame parameters 1.4 MB, drain worker UE 5.7 MB, compact fallback 739 KB) are `NR_CELL_STATIC_HEAP`, allocated before the RX fence by the prepare / `nr_csirs_blind_rt_cell_prealloc()` (called at the top of `nr_csirs_disc_pipeline_init`, which runs bound for every cell, N=1 included). `g_zp_maint` (90 KB) and `g_csirs_obs` (82 KB) stay BSS arrays because diagnostics/metrics may touch them on any slot (no fence-gated heap). The extern `csirs_disc_*` counters stay PROCESS (aggregate telemetry). The `[sensing] csirs_monitor` list belongs to the command-line cell (parsed on cell 0 only).
- Test `test_nr_csirs_cell_iso` [OFFLINE VERIFIED]: one thread re-binding and two bound threads; prepare of a second grid, disable isolation, monitor isolation, epoch remove-all per cell. Built against the base sources it FAILS at line 72 (`prepare(&small) == 0`); with the fix it passes.

### RC2 PDCCH nID GPU sweep was one worker for the process [CODE-READ + REPLAY VERIFIED + unit]
`nr_pdcch_nid_gpu.c` kept one `g` (device window, batches, duty, records) started with cell 0's N_RB. After RC1, cell 1 also armed it: its batches reset the duty/records on every geometry change, and its records were readable by cell 0. Evidence: 2-cell run with RC1 fixed only (dbg2_f1, 120 s): cell 0 `PDCCH_NID_GPU pass` = 1 vs 93 solo (120 s).
- Fix (629c905275): state per cell (`NR_CELL_STATIC_INIT`), worker created with `nr_cell_thread_create` bound to the starting cell, cell k>0 started in `mpci_cell_prealloc` (cell 0 unchanged in main), stop per cell at shutdown. The device module refused a second context ("one pre-RX context per module lifetime", `nr_dl_gpu_sealed`): `create()` now lifts the module fence for one create while `nr_gpu_allocation_guard()` still allows allocations (before the RX seal) — first evidence: `PDCCH_NID_GPU init failed; capture disabled` for cell 1 in dbg2_f2; after the fix cell 1 runs 60-140 passes.
- Test `test_nr_pdcch_nid_cells` (fake device module) [OFFLINE VERIFIED]: own worker, records, passes, stop per cell. Against the base worker it FAILS at line 52 (`!nr_pdcch_nid_gpu_running()` on cell 1); with the fix it passes.
- Not fixed (noted): `nr_gpu_membudget_commit(NR_GPU_MEM_PDCCH_NID, ..)` replaces the module figure per create (accounting only, as A7 noted for CSI-RS); all cells' nID workers pin to the same nID core (B5/G2 item); `nr_gpu_budget_discovery_prefer` is a process flag toggled by every worker.

### RC3 initial-sync PSS fold and capture start were process-wide (heap corruption) [CODE-READ + REPLAY VERIFIED]
`pss_nr.c` `s_pss_fold` is reset and re-sized (period = 2 x decimated samples, different per cell) by whichever cell's SSB scan runs; the scans run on the shared Tpool, so two cells' scans wrote into one accumulator with different periods while the other reset it (heap overflow / use after free). `nr_initial_sync_capture_start` was a global set and cleared around `nr_initial_sync` by both sync actors. Evidence: base 2-cell log has `[c0] PSS_ACC ... abs=30727680` (cell 1's 30.72 MS/s capture tagged as cell 0, reset to captures=1) and no cell-0 PSS_ACC at all; after the fix `[c1] PSS_ACC abs=30720000 captures=1,2` and `[c0] PSS_ACC abs=122880000 captures=1,2`.
- Fix (b53b612c06): `nr_ue_ssb_scan_t.cell` = the queuing cell, `nr_scan_ssb` runs bound to it and restores the Tpool thread's binding; `s_pss_fold` per cell; capture start `__thread` (set and read on the cell's sync actor). Not unit-tested: the fold is only reachable through the full PSS search; covered by the replay evidence above.

### RC4 legacy GPU exact FEP initialised for cell 0 was used for cell 1 (heap overflow at exit) — fixed by mpci-main G3b [REPLAY VERIFIED + CODE-READ]
After RC1-3 the exit still aborted (`corrupted size vs. prev_size` in `iq_ddc_free`, radio_shutdown). A write-only ASAN build (`--param=asan-instrument-reads=0`, diagnosis only, not committed; DEEPBIND and aligned_alloc worked around locally) found no instrumented write overflow during RX; with a temporary pointer trace, the corrupted allocator chunk was right after cell 1's PDSCH consumer `rxdataF` (0xf51e6e868800 + 229376 B -> 0xf51e6e8a2000). Writer: the GPU exact FEP (uninstrumented device copy), initialised with cell 0's geometry (N=4096, 217 PRB) and called for cell 1's 1024-FFT buffer; the log shows `[c1] GPU_EXACT_FEP self-check MISMATCH at slot 13 -- GPU FEP disabled` (it also disabled the GPU FEP for cell 0). mpci-main G3b (696f8b96a2) added exactly this guard in `exact_run` (another geometry -> CPU FEP) and per-geometry pass FEP; merged (77ef2a8a4f). After the merge: no MISMATCH, clean `SHUTDOWN step=complete`, no free()/corrupted/ISAC_SEGV in the 120 s and 240 s 2-cell runs.

Two pre-existing out-of-bounds READS seen by ASAN, not fixed (not multi-cell, N=1 identical, out of scope): `nr_pbch_dmrs_correlation` reads up to k=Nid%4 samples past the row (`&rxdataF[aarx][k]` + `re_offset` < N), and `signal_energy_nodc` SIMD over-read (16 B) at the end of the PUSCH rxdataF in `nr_rx_pusch_group_internal`. Also `nr_gpu_pass_ul_prewarm` calls `aligned_alloc(64, 0x66a0)` (size not a multiple of the alignment; glibc accepts it).
