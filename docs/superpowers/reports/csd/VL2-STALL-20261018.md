- Outside this window the run is normal: UL tot p50 0.87 ms; of 12014 UL_E2E lines, 130 of the 140 above 10 ms lie in the window; 116 of 133 DL lines above 10 ms lie in it.

  - DL: qwait (enqueue->dequeue) median 8 us -> 5.6 ms in the first bin, then dec stage 0.5 -> 3-6 ms. Per-code-block decode time doubles: 185 us/cb in the window against 106 us/cb in the rest of dVL2 (grants with cb>=8). PDSCHQ lag up to 43 slots; pdschq_drop_stale 51 at end of run.
  - Not growing: PDCCH scan (no SCANTIME/DCI scan outliers; PDCCH keeps up until DCI count drops to 0 at the end), GPU wait counter of DL (pdschq_latency.gpu_wait all 0), FEP cache.
- UL secondary effects at the end-of-run counters: UL_GPU_FEP max_us 25934, over_cap 166, late 21 (all 0/<=1.6 ms before the window); UL_GPU_LDPC busy 4, deadline 5, late 10, reclaimed 5; PUSCHQ2 real full=4 (was 0) = UL grants dropped at queue depth 32.

## 5. Most likely cause

[INFERRED] A positive-feedback loop that starts with GPU contention under a sustained, wide, 4-layer DL burst, then moves to CPU:
1. 100 Mb/s of DL (6.2k code blocks per 0.5 s, 4 layers, 217 PRB, chest+demod+LDPC on the GPU) saturates the RT GPU partition. [MEASURED part: load, DL per-cb decode time x1.75-2.2, GPU calls slow; INFERRED part: that the queueing is behind DL kernels.]
2. UL FEP/LDPC streams are created at the LEAST priority in the same RT partition (ISAC_UL_GPU_PART=rt; nr_pusch_gpu_diag.h:33-45, "DL streams outrank them; a running UL block is never preempted"). UL FEP kernel took 2-26 ms to complete [MEASURED].
3. `nr_pusch_gpu_fep_run` (nr_pusch_gpu_fep.cuh:185-248) waits with no deadline ("a late kernel is waited for, never abandoned"), then charges the whole wall time `dt` to the 100 ms duty window (`U.win_used_us += dt`, cap 30% = 30 ms). One 26 ms call nearly exhausts it, then over_cap -> CPU FEP (166 times) [MEASURED counter]. UL LDPC (nr_pdsch_gpu_ldpc.cu:1085-1125) has a 4 ms deadline and the same cap, so it fell back to the CPU (ldpc:g0, cpu_us 2-3.7 ms) [MEASURED].
4. UL consumers (2 threads, cores 0,1) now spend 2-4 ms per grant on CPU FEP+LDPC, against a UL arrival of about one grant per 0.5-1 ms (40-70 UL DCI per 100 ms plus probes), so the queue (depth 32) fills; arr2deq climbs to 40-60 ms, 4 grants dropped as full [MEASURED]. The UL queue has no stale-drop (only `full` and `epoch`, nr_pusch_passive_queue.c / nr_passive_metrics.c:162), unlike PDSCHQ (stale=51), so it drains the whole backlog instead of skipping old grants. This is why a 0.6 s GPU event becomes a 0.6 s UL latency of 40-60 ms.
5. The DL slowdown is consistent with the same shared GPU (per-cb decode time x1.75-2.2) plus CPU load of the UL fallback [INFERRED]; DL cores (7,8,9,3,4) and UL cores (0,1) are disjoint, so a CPU-core conflict is not supported by the log, but memory bandwidth/L3 sharing is not excluded [not measured].
Alternative explanations rejected on the log: RF/ring stall, reconfig/PCI/SIB, BGDISC, NID GPU pass (no correlation over 140 passes), layout lock, log backlog (no evidence).
Not excluded: a second, independent GPU client (CSI-RS discovery FEP chunks, "feed_drops" 1->1530 in the same window) adding to the saturation; the log cannot separate the share of DL vs discovery. ISAC_GPU_BUDGET=1 / DISCOVERY_BUDGET_PCT=30 are on, so the discovery chunks are supposed to yield; the feed drops say it was starved or throttled in the window.

## 6. General fix proposals (not cell-specific)

1. Bounded UL GPU FEP wait: give nr_pusch_gpu_fep_run the same hard deadline as UL LDPC (about 1 ms; kernel writes into private pinned rows, copy on success, abandon the context like `UL.lost`), so a starved UL call costs 1 ms, not 22-26 ms, and the CPU FEP (about 0.1-0.2 ms/grant) takes over [INFERRED benefit, needs measuring].
2. Charge the duty cap with kernel time (event time) or launch-to-first-poll, not wall time including queue starvation; and add a hysteresis ("DL burst" = GPU calls late twice in a row -> go CPU for the next N ms) so UL does not oscillate GPU/CPU.
3. Stale-drop in the UL queue: grants older than a latency budget (e.g. 8 slots = 4 ms, like PDSCHQ stale) are dropped/diverted, so a stall costs a few grants and the p99 returns to 3 ms after the burst instead of draining 60 ms of backlog. Counts as UL drops; the scorer drop metric is 0.1 % now, so the budget is available.
4. Optional: a third UL consumer (or CPU-only fast path for 3-PRB MCS 27 grants, which are the bulk of UL_E2E: prb=3, mcs=27) only while arr2deq > 2 ms. Larger change; only if 1-3 are not enough.
5. Diagnostics to add: log UL queue depth and the GPU partition occupancy on a ULSTALL line, print an "UL_STALL_SUMMARY" per stall episode (start t, end t, max arr2deq, max FEP gpu_us, DL cb/s), so this analysis does not need reconstruction from utc anchors.

## 7. Replay test that should reproduce it (not run)

- Needs a DL load of at least 100 Mb/s decoded (4 layers, 217 PRB, tbs about 100-180 kbit, one grant per slot for >= 0.6 s) with a concurrent UL PUSCH stream of about 40-70 grants/100 ms (3-PRB MCS 27). The dVL2 stall is not capturable now (no IQ capture of this run is referenced in the report); a synthetic version: use tests/passive_rx/dgx/rfsim_regress.sh-style rfsim with a high-rate DL generator plus UL, env t26uL, ISAC_UL_STALL_DIAG=1, ISAC_E2E_TRACE=1, ISAC_UL_GPU_PART=rt, with the idle-host flock for measurements.
- Pass criteria: no ULSTALL fep gpu_us > 4 ms (or, with fix 1, ULSTALL bounded at deadline), UL_GPU_FEP over_cap == 0, UL arr2deq max < 5 ms, UL tot p99 < 3 ms in the burst window, and DL dec/cb not slower than 1.3x the baseline. Without fixes expect the signature in section 1 (UL_GPU_FEP max_us >> 2000, over_cap > 0, arr2deq tens of ms).
- Control: same replay with ISAC_UL_GPU_FEP=0 ISAC_UL_GPU_LDPC=0 (CPU UL) shows whether UL alone survives the burst; and with t26uC (UL cores 5,6) to see whether CPU placement matters.
