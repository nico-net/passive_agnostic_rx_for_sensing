# ULFEP-20261014: GPU front end for the passive PUSCH decoder

Branch `csd/ulfep` (from csd/ulq d3db97de2e), build `build_t26` (DGX GB10). Labels: `[MEASURED, DGX replay <capture>, p99_replay.sh SPEED=1,
t26bPQ.env, sd_t26ul.cfg, 4 RX, ULQ Q-arm on cores 0,1, ISAC_PUSCH_TIMING=1]`, n = 3 per arm, interleaved off/on, one replay at a time
under heavy.lock, host idle (other user gone from ~18:25). TIM = PCI 923 tile3, b = Vodafone PCI 415 12s_b; never pooled.

## 1. FEP cost breakdown (step 1) `[MEASURED, replay tim, UL_FEP_REQ]`
Per grant the UL FEP asked for ~2134 grants: 118 k FFTs (grant symbols, 38 %), 161 k (timing-discovery search, 52 %), 28 k (delay re-run, 9 %).
The grant already FEPs only its own PUSCH symbols and all 4 antennas. The 4096-point FFT cannot shrink; the only CPU-side saving
(rotation only on the granted PRBs) is ~10 % and was not done. More than half of the FEP is the timing search: up to 33 + 17 candidate
advances x 4 antennas for one symbol, scored one by one. That is why the GPU path batches candidates.

## 2. What changed (all default off)
- `ISAC_UL_GPU_FEP=1`. New `nr_pusch_gpu_fep.cuh` (included at the end of nr_pdsch_gpu_fep.cu, exported by libpdsch_gpu.so) + host glue
  `nr_pusch_gpu_fep.h`; hooks in nr_pusch_passive_decode.c: grant FEP (one launch per call), timing-search candidates (one launch per phase,
  scores read scratch rows), delay re-run, and the layout probe (5 symbols x 4 ant, bare DFT).
- Reuses the DL bit-exact int16 kernel pieces (nr_exact::fft4096, rotation arithmetic, tables). Own item table, own 4 contexts, own streams
  on the discovery SM partition (ISAC_GPU_DISC_SMS / ISAC_GPU_RT_ISOLATE) else lowest priority + deferral while an RT GPU user is in flight
  (new read-only `nr_gpu_budget_rt_active()`). Duty cap `ISAC_UL_GPU_FEP_PCT` (default 30 % of each 100 ms); over cap / all contexts busy /
  outside the snapshot / fo_hz != 0 / error -> unchanged CPU FEP, counted. Wait = poll, 60 us spin then 25 us nanosleep (no busy spin).
  All tables, streams, item tables created at warm-up (UL queue start, before the RX seal); host buffers already written (malloc16_clear).
- `ISAC_UL_GPU_FEP_CHECK=n` (default 16): every n-th call one row is recomputed on the CPU and memcmp'd; mismatch -> GPU off for good.
- Census: `UL_FEP_REQ`, `UL_GPU_FEP on= calls= items= gpu_ms= mean_us= max_us= busy= over_cap= rt_defer= late= err= part= | cpu_bounds= cpu_rej= check= bad=`.

## 3. Equivalence `[OFFLINE VERIFIED / MEASURED]`
- Unit test `test_nr_pusch_gpu_fep` (new, ctest, skips without CUDA): GPU rows == dft + apply_nr_rotation_symbol_RX, 0 of 576 rows differ for
  uniform input amplitudes up to +-3000 (rms 1700), N_RB 51/106/217/273, rotate 0/1. KNOWN LIMIT: from uniform +-4000 (rms 2300, all samples) the
  CPU saturates in butterflies the shared kernel does not reproduce (128-512 of 4096 bins differ; this is a property of the DL exact FFT too).
  Real UL captures have rms 290 (TIM) / 750 (b), peaks 7.8k / 13.4k.
- Replay with CHECK=1 (every call): 5611 compared rows, bad = 0. n=3 runs per capture with CHECK=16: bad = 0 in all 12 on-arm runs.

UL per-grant cpu_us (ulq_stats full decodes) p50, then p99:

| capture | off (3 runs) p50 / p99 ms | on (3 runs) p50 / p99 ms |
|---|---|---|
| TIM | 8.8 / 53.6, 7.6 / 33.8, 9.0 / 49.0 | 7.1 / (1 stall), 2.9 / 68.0, 3.4 / 26.8 |
| b | 4.0 / 777, 5.5 / 768, 2.7 / 365 | 1.3 / 258, 1.5 / 369, 1.6 / 361 |

p50 drops ~2.6x (TIM) and ~2.5x (b). p99 is NOT improved: it is dominated by stalls outside the FEP (decode max 0.1-1.5 s, UCI/rescue search and
queue waits); n is small and the full-decode count varies 48-1830 per run because layout lock is not reproducible in replay. No UL CRC-OK in any
arm (as in ULQ). UTIM fep mean (all runs): TIM off 2.9-5.4 ms -> on 3.7-5.0 ms mean but with 4.7-8 % of calls at the cap falling back to CPU on
the slow little cores; b similar. Real-grant loss: queue `full` drops 0 in the on arms shown; not separated further.
GPU call latency: idle GPU bench (8 SM partition) 14 items x4 ant = 138 us, 33 items = 215 us, 5 items = 50 us (CPU: ~0.6 / 1.3 / 0.25 ms).
In replay the mean call is 0.4-2.5 ms and 35-84 calls per run last > 2 ms, max 53-233 ms `[MEASURED, open]` (see risks).

DL impact `[MEASURED, same runs]`: PDSCH real-grant p99 us, TIM off 5005/3285/6315 vs on 4515/4625/5285; b off 3645/2565/2835 vs on 3095/3445/2985
(one on-run max 206 ms, off max 11-58 ms: single outlier, unexplained). gpu_budget_used_pct TIM off 21.4/22.7/22.7 vs on 21.9/22.5/21.4; b off
19.9/19.2/20.0 vs on 19.6/20.4/19.0; rt_gpu_wait_max_us 0 and rt_gpu_fallbacks 0 everywhere. No DL degradation resolvable at n = 3.

## 6. Risks / open
- GPU call tail: 35-84 calls per run > 2 ms, up to 233 ms. Cause not isolated (could be CPU preemption of the consumer on cores 0,1 while it sleeps, or
  GPU/host-memory contention). The kernel writes the caller's rows, so a late call is waited for, never abandoned: it delays the UL consumer only
  (not DL), but it keeps UL p99 from improving. Do not default-on before an OTA/replay with GPU-side event timing.
- Bit-exactness holds for realistic amplitudes only (section 3); the runtime check turns the path off on the first mismatch it samples (1 in 16).
- Duty cap 30 % sends 4-8 % of calls to the CPU; raise only with a DL p99 A/B.
- Only fo_hz == 0 (no --cont-fo-comp), N = 4096, <= 4 RX, snapshot-backed grants. Not covered: UL LDPC (still CPU).
- The module fence is lifted for the UL init only (nr_pusch_gpu_fep_init), still before the platform RX seal.
