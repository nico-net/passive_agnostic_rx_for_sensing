# DL-HEALTH (2026-10-29): health check of DL discovery and DL decoding on the OTA runs of 2026-10-26 / 10-28

Read-only analysis of existing logs under `/home/nicola/NICOLA/ota_runs/`. No receiver, replay, build or radio was run. Nothing is committed.
Host for every log: DGX Spark (aarch64) + X410 34B2AF1 (DPDK), 4 RX, GPU pass on (Iliad: CPU path, see 3.7). Cells are never merged across cells, hosts or bandwidths.

Label key (PROJECT_MEMORY §0.1 style): `[MEASURED, DGX+X410 34B2AF1, <date time>, <cell>]` = a number read from that run's `run.log` (ANSI stripped) or from
`goal_metrics.py` on it; `[CODE-READ]` = read in `/home/nicola/NICOLA/wt/rr-mpci-main`; `[INFERRED]` = follows from measured facts but not isolated;
`[HYPOTHESIS]` = not tested. All runs are n=1 and 270-300 s long; traffic differs between runs (time of day, UEs), so solo vs 2-cell comparisons are
only meaningful for time-adjacent runs (mp28m_* 07:18-07:52) and are marked.

Method and its limits:
- Scorer: `python3 tests/passive_rx/goal_metrics.py run.log` (per-cell blocks for multi-cell logs). "tot" = EVMGRANT `e2e` field 7 (slot arrival to end of decode).
- Everything else was extracted with throw-away scripts (scratchpad, not committed) from the same logs: acquisition events, EVMGRANT (probe=0, skip=0, non-SI RNTI) CRC by
  MCS/rank/RB, `e2e` components, ISAC_METRICS, PDSCHQ, GPUGRAPH, PDTIMPCT, CORE_POOL, ULSTALL, RFCENSUS, DECODETDRA, RECOV.
- Times in "timeline" tables are interpolated between ISAC_METRICS `abs_slot` anchors (one per ~10 s): resolution is about +-5 s, so events earlier than ~10 s
  are quoted as "<10 s". Ordering and the larger values are reliable.
- My "C-RNTI CRC" in the breakdown tables counts non-SI-RNTI EVMGRANT with probe=0 and skip=0 (a full decode attempt). The scorer's `crc_all` also counts grants
  skipped by the DM-RS SNR gate, so the two differ by construction. Where they could be confused, the scorer name is used.
- Runs used: solo `sw28_S415_1_085821` (Vodafone), `sw28_S923_1_091115` (TIM), `mp28m_S1_1_071826`, `mp28m_S2_1_073108` (Vodafone), `il28_A1/A2/A3` (mpci-main 8ed7059411),

## 4. Co-channel PCI locking (sw28_P1 cell 0 locked PCI 380)

Facts [MEASURED, DGX+X410 34B2AF1, 2026-10-28 09:04, sw28_P1 cell 0]: `cells.json` lists `pci415 ssb_index 4, cfo_hz -4827`; `MPCI_LIFE ... primary=pci415`. Scan 1: PSS peak at noise, `SCAN_PBCH_FAIL pci=324`. Scan 2 (next
capture): `Initial sync: pbch decoded sucessfully, ssb index 1` -> `Initial sync successful, PCI: 380`, no SSB_MULTI_PCI line (one SSS candidate only). Then `BCCH update: phyCellID 0->380`, SIB1 of 380 decoded at ~2 s, `CORESET#0`
verified, but no dedicated CORESET, 9 C-RNTI grants in 270 s (cell 1, TIM: 58257). Cell 0 stayed on 380 for the whole run, with no event: no "PCI mismatch", no re-scan.

Frequency (all 2-cell runs under `ota_runs/` that have a `cells.json`, descriptor PCI vs `Initial sync successful`):
- 24 cell instances reached sync; 2 locked a PCI different from the descriptor: sw28_P1 cell 0 (415 -> 380, ssb idx 1 instead of 4) and mp28m_Q1 cell 1 (Iliad 403 -> **27**, idx 1 instead of 3; SSS list `27:10348 crc_ok, 459, 837` has
  no 403; that cell then verified a CORESET at ~35 s, had 0 solves and 3 C-RNTI grants, DL block n_real 310).
  (The sw28_R1/R2 "mismatch" in a naive comparison is the reversed cell order, not a wrong lock.) So 2/24 = 8 %; each costs 100 % of that cell's grants.
- All 18 other instances locked the descriptor PCI on the first or second scan. The other solo runs always locked the expected PCI, but they are not checked against anything either.

Why [CODE-READ]: `executables/nr-ue.c:208` sets `ue->target_Nid_cell = -1` and the initial-sync request has no PCI; `nr_search_ssb_common` accepts the first SSS candidate whose PBCH CRC passes
(`nr_initial_sync.c` ~L525: candidates in SSS order, first `crc_ok` wins). The MPCI descriptor's `pci` / `ssb_index` is used only for naming and for the per-cell registry
(`MPCI_CELL ... pci=415`, `common/utils/nr_cell_mgr.c`). `grep` for a comparison of the synced PCI with the descriptor PCI finds none (only `nr_pdcch_ul_layout_lock.c` resets on PCI change). The code path to pin
exists (`target_nid_cell >= 0` restricts `rx_sss_nr`), it is not set at first sync. Co-channel neighbours of the 3680.01 MHz carrier (PCI 380, 249, 748, 713, 582 from CSI-FULL / SNR-AUDIT) and a second Iliad sector are
in the same SSB window, so a capture in which the wanted SSB is not decodable returns the neighbour.

## 5. Why both Vodafone codex runs never synced (codex_uldld_vodafone 2026-10-28 21:25, codex_existing_vodafone 21:30)

Facts [MEASURED, DGX+X410 34B2AF1, 2026-10-28 21:25-21:35, Vodafone 3680.01 MHz]:
- 370 and 393 consecutive scans, each `SYNC_SCAN ms~660 gscn=1 ant=4 frames=2 detected=0` then `synch Failed`; no `Initial sync successful`, no SSB_MULTI_PCI line (no SSS candidate ever passed), so

  (`mpci-main 8ed7059411`); codex_uldld used `ul-dl-validation 3f1dee1a69` (no GPU module, 3 scan worker threads). So it is not the branch.
- The same session synced Iliad (21:20), TIM (21:35) and Iliad (21:40, 21:46) on first attempt. The day before (`mp27e_*` 21:20-21:32) Vodafone synced on every run.
- `PSS_DECIM` (decimated, 8-capture accumulation) does see a PSS: in every second capture (the one 10 ms later) nid2=1 (415 mod 3) stands 6 dB above the other two hypotheses (31.8 vs ~25 dB), which is the same
  margin as in a successful scan (25.5 vs 20/22.9). The full-resolution stage then finds no SSS/PBCH.
- Input power at the start of the codex Vodafone runs is higher than in the morning: `CHPOW` ch0..3 -24..-28 dBFS (uldld), -29 -> -43 dBFS over 2 s (existing) vs -38 -> -61 dBFS (sw28_S415 09:03); `CHRMS` 379 / 115 vs 147. [MEASURED]
- No ADC clipping can be read (ADCPEAK/ADCCLASS print only after sync).

So the log shows: the PSS of the wanted cell is present, the SSS/PBCH stage fails every time, with an unchanged CFO seed and no search widening. I cannot name the cause from the logs. Candidates, none
tested: (a) the true CFO moved outside what the seeded PSS/SSS refinement tolerates (the seed `-4827` Hz is a fixed per-cell constant from a previous session, `fo_pss` values scatter between -6.2 and +10.4 kHz; TIM's seed
works because its offset did not move) [HYPOTHESIS]; (b) a 10-12 dB higher in-band level (busier evening, or a new interferer) compressing the front end or masking the SSS [HYPOTHESIS]; (c) the Vodafone SSB
itself changed (beam / power-saving / SSB periodicity) for ~10 min [HYPOTHESIS]. What is certain: the acquisition loop has no escalation (same seed, same raster point, same window for 370 attempts), no explicit
"cell not found" state, and the run produced 0 grants for 4.5 min with exit 130 only because the operator stopped it. Discriminating test: repeat one Vodafone start with `--initial-fo` 0 and +-3 kHz and look at `SCAN_PBCH_FAIL fo_pss/fo_sss`
and the decimated PSS level; or log the PSS-folded CFO estimate on the strong second capture.
