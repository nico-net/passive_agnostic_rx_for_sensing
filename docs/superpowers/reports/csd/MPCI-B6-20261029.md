### Value order (item 4), from what the code already knows (FLOAT-LANE-POOL inventory, call sites)
Lowest value, shed first:
- tier 0: `UL_DISC` (ulBgDisc, HOUSE: "none" latency sensitivity, nothing waits for it);
- tier 1: `CSIRS` (csirsDisc: "drop/defer already built in"), `DMRS_ID` (verifier/estimator: "none");
- tier 2: `JANON` (speculative DCI search: items older than 1 s are dropped), `NID` (acquisition sweep, re-run every 250 ms in maintenance).
Never shed: decode of a found grant (DECODE), retry (RETRY), the PDCCH scan (SCAN: it is how grants are found, and its own queue already drops the oldest occasion), and the decode-gating helpers `DMRS_SCAN`, `USS`, `PROBE` (they decide whether a grant can be decoded at all; PDSCH CRC is never traded for latency because the decoded payload is used for sensing). The task's order (decode > retry > scan of new candidates > discovery > housekeeping) is the order of what is dropped last; the pool keeps its class priorities (SCAN first because it feeds decode).

### Not done, and why
- **PDSCHQ drop policy (prefer dropping probes and repeat grants of a failing RNTI before locked-RNTI grants)** and the scan-queue "least information occasion first": both live in `nr_pdsch_passive_queue.c` (A11) and `nr_pdcch_passive_queue.c`; the first is A11's file, and neither is a token-level lever. After this change the scan queue is still drop-oldest; whether it still overflows is the measured STOP.
- `GPU_EXACT_DEMOD` (73 ms) is not sliced: GPU wait, not a CPU loop.
- The CHAN reserve in the admission table is 1 token (the GPU backend's demand); a CPU backend asks for more (`k` threads) and is not known at admission time.
