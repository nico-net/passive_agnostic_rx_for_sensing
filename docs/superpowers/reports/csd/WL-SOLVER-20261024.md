# WL-SOLVER: Iliad and WindTre solve no C-RNTI (2026-10-24, branch csd/wl-solver from e9c874c308)

Hosts: DGX Spark (aarch64), X410. All numbers [MEASURED, DGX replay] unless labelled. Cells are never pooled.

## Iliad PCI 403 (51 PRB, NSA)
Root cause [MEASURED, DGX replay + CODE-READ]: DCI 1_1 length 48 at BWP 51 cannot be explained by the standard field profile
(riv 11 bits + bwp_ind <= 2 + tda <= 4 = max 47 bits). `nr_pdcch_blind_dl_layout_candidates()` therefore returns n = 0 (the optional-field
fallback is ambiguous, > 3 layouts). In `nr_pdcch_blind_monitor_rt.c` the `if (!n) continue;` before the solver branch dropped EVERY
C-RNTI DCI 1_1 before the PDSCH solver (which reads the resolver's own 2521 layouts) saw it: 12 "DL raw evidence" lines, zero solver activity.
Vodafone/TIM never hit it because their length is explained by the 3-candidate profile.
Fix (rt.c, small; nr_pdsch_solver.c NOT touched): with the solver enabled, dl_auto and the resolver armed, n = 0 no longer drops the grant;
the first live resolver layout that parses the payload is used as the representative `out` (rnti/rv/mcs only feed solver admission gates).
Pure gate `nr_pdcch_dl_solver_fallback_ok()` + gtest `DlLayoutCandidatesEmptyAtIliad51PrbLen48ButSolverFallbackAdmits` (passes; it also pins the precondition n == 0 with a real OTA payload).
Replay raw_iliad403_4s_1023_2315 (4 s), before -> after: solver messages 0 -> 2747; non-SI EVMGRANT 0 -> 1357 (all solver probes); stage 1
hard-refuted type 1, RA type 0 cfg1 armed (1706 layouts). solved RNTIs 0 -> 0, C-RNTI CRC 0 -> 0: NOT solved in 4 s of night traffic.
Hand-decoding of the 17 logged payloads [INFERRED]: fmt 1 | bwp_ind 1 bit (always 1) | RA type 0 bitmap 13 bits (RBG 4) | TDA 4 bits | standard tail,
MCS mostly 20-26 (64QAM+). That layout (type 0, bw=1, td=4) is inside the armed set, but two solver policies keep it from being probed:
(a) one-layer-QPSK preference (nl_preferred): wrong layouts always offer a garbage QPSK reading, so the true 64QAM reading is never in the preferred set
(probes seen: all Qm 2, none with rb 0+51); (b) SOLVER_SEARCH_MAX_RB 48 excludes full-band 51 RB readings (csd/solver-wide domain).
Not changed here (frozen/other branch); a 300 s OTA run may or may not get past this.

## WindTre PCI 508 (162 PRB)
Root cause (partial) [MEASURED]: different from Iliad. No DCI 1_1 ever reaches the solver stage: zero "DL raw evidence", `DCI 1_1 length locked` once,
0 bank adds; dedicated CORESET discovery ends MISSED. The SI-RNTI link itself is bad: SIB1 PDSCH CRC ok 2 of 3833 attempts, per-grant SNR p50 1.7 dB
(p90 3.2) vs Vodafone p90 18.6, Iliad p50 6.4; branch SNRs strongly unbalanced (one branch +3.7 dB, others -5..-8); PBCH rsrp 38 (adjust_rxgain +12 dB).
Capture PSD [MEASURED, raw_windtre508_4s_1023_2315]: carrier +-29 MHz sits ~14 dB over noise, but an adjacent signal at +30..+60 MHz is ~10 dB STRONGER
(85-88 dB vs 75-80). At 61.44 MS/s (decim 2) that neighbour is at/over Nyquist; aliasing/ADC blocking is the leading hypothesis for the 2 dB EVM-SNR [INFERRED, untested].
Replay (4 s, decim 2) reproduces the weak link: SIB1 never decodes, 3 non-SI EVMGRANT before and after the fix (identical), so 4 s is too short to reach discovery;
WindTre cannot be validated from this capture. No WindTre fix is claimed; the fix above does not apply (n > 0 for 162 PRB: bw+td = 4).
