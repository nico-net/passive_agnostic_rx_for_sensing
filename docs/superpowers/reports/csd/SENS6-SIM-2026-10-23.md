## Headline

- The tree builds on sens6 only with workarounds (section 2). `libpdsch_gpu.so` does not build with CUDA 12.4 at this HEAD.
- The 4-RX 106 PRB gate FAILS on both arms. Cause is functional, not performance: the PDSCH solver (default-on since `0fb22ecbd0`) never decodes a full-carrier grant, so 0 PDSCH are decoded. A gNB with `-M 40` decodes (section 5, diagnostic).
- No crash after `9aef537ffb`. Round 1 (e9c874c308) crashed at ~10 s on a misaligned DFT buffer.
- 273 PRB rank 4 (pinned conf) works on CPU: 3462 grants, CRC 100 %. 273 PRB rank 1 auto fails like 106 PRB.
- All DL decode runs on the CPU: the discrete-GPU backend does not exist on this HEAD. The receiver still holds 7.4 GB of the 8 GB GPU.

What did work [MEASURED, sens6 rfsim]: PBCH sync at 9.5 s / 9.8 s, `RFCENSUS pbch_ok=50/50`, gNB healthy (RNTI 0x1234 in sync). The first `rnti=` lines (43.4 s / 36.4 s) are junk RNTIs (`ANONLEN_AUDIT_MISS`, `DCIQUAL`). `dci10 accepts 27`, `dci01 accepts 28229` (noise), `pdsch_decode try=0`.

Root cause [READ code + MEASURED, sens6 rfsim]:
- The PDSCH solver (`ISAC_PDSCH_SOLVER`, default on since `0fb22ecbd0`, 2026-10-18) probes only readings up to 48 RB: `openair1/PHY/NR_UE_TRANSPORT/nr_pdsch_solver.c:14` (`SOLVER_SEARCH_MAX_RB 48`).
- The solver block in `nr_pdcch_blind_monitor_rt.c:8532-8971` ends in `continue`, so a full-carrier DCI 1_1 (106 PRB here, 273 PRB in B1) is consumed by the solver and never reaches Technique D.
- Control run `dbg_nogpu` (GPU hidden from the process): identical, `decoded=0`, `n_contexts=0`. The GPU is not the cause.
- Control run `dbg_m40` (gNB `-M 40`, grants of 40 RB, 180 s): the receiver decodes (section 5). Hence 4 RX and sens6 hardware are not the blocker.
- Status: the solver wide-grant fallback is being fixed by the user, together with the rfsim gates on the DGX/Spark. The sens6 gate is to be rerun after that. Not tested here: 1 RX at 106 PRB.

## 7. Ranked changes needed for sens6 (nothing implemented here)

1. Solver wide-grant fallback. Grants wider than `SOLVER_SEARCH_MAX_RB 48` (`nr_pdsch_solver.c:14`) must fall through to Technique D instead of `continue` (`nr_pdcch_blind_monitor_rt.c:8532-8971`). Blocks the gate at 106 PRB and 273 PRB rank 1, hence all of sens6 and probably OTA at 80/100 MHz. Owner: user, in progress.
2. Discrete-GPU backend. Branch `sens6/discrete-gpu`: T1 (CUDA compat shims `d89db002eb`), T2 (arch list), T3 (3-tier platform `c386fb8767`) and T4 (DIRECT-only guards) are done; T5-T11 pending (plan `docs/superpowers/plans/2026-10-23-discrete-gpu-backend.md`). Until then sens6 decodes on CPU only.
3. Build blockers on the main line: `_GNU_SOURCE` in `nr_gpu_pass_dl.c` and `nr_pdsch_passive_decode.c`; `#include <algorithm>` in `nr_pss_decim_test.cc` and `nr_srs_blind_test.cc`; the CUDA >= 12.5 shims from T1.
4. `add_dependencies(nr-uesoftmodem pdsch_gpu)` (`openair1/PHY/CODING/CMakeLists.txt:180`) makes the receiver unlinkable whenever the optional GPU library fails. Make it optional.
5. GPU memory footprint: 7.4 GB held at 0 % utilisation on an 8 GB card leaves no room for the discrete backend's device buffers. Size the pre-reserve from the device (or lazily) when the DISCRETE tier lands.
6. RAM: 14 GiB with 4 GiB hugepages; B1 ended with 397 MB free and swap in use, RSS up to 7.7 GB. Needs a budget check before OTA.
7. `UEthread_0` single-thread hotspot (96-98 % of a CPU) in rfsim; any extra load per slot lands on it.
8. `score_rx.py` counts only `Technique D CONVERGED` (and `SWEEP: ... CONVERGED`) lines as contexts [READ code score_rx.py:49-65], so a run that decodes through the solver shows `n_contexts 0`. Count solver solves (or make the gate accept either) once item 1 lands.
9. Test fixes: `test_nr_pdsch_gpu_demod` (aligned test data, `9aef537ffb`-style 64-B alignment), `test_vrtsim_cirdb` (shm race), `nr_pusch_ra0sim` link (blocker 7).
10. CAP_SYS_NICE / pinning policy: without it the affinity plan is not applied and threads float. Decide between granting the capability to the launcher (as OTA does) and accepting floating threads for rfsim; the pool list then only limits concurrency.
11. Float-lane "W >= 8 merged" rule: not implemented; low priority at W = 12 (measured float lane peak 57 % per CPU, never saturated).
12. Hardcoded cores 15/16 and the dashboard on CPU 2: harmless in rfsim; revisit for the sens6 OTA launcher.

## Appendix: round 1 crash (fixed)

Round 1 (e9c874c308): both 106 PRB 4-RX arms exited after 10.1 s / 9.97 s: `Assertion (((intptr_t)output & algn) == 0) failed! In dft_implementation() oai_dfts.c:3441 "Buffers should be aligned"`, output pointer ending `...990` (16-aligned, not 32) [MEASURED, sens6 rfsim]. gdb backtrace (also at 1 RX): `dft_implementation` <- `nr_csirs_disc_fft_cpu` (`nr_csirs_disc_td.c:74`) <- the traffic-probe worker (`nr_dl_traffic_probe_rt.c:104`), whose DFT buffers were `malloc` (16-B) at `:217-224`; the same pattern was in the SRS FEP [MEASURED, sens6 rfsim] `gdb_align/backtrace.txt`. AVX2 needs 32-B output alignment; NEON only 16 B, so aarch64 never saw it [INFERRED]. Fixed in `9aef537ffb` (64-B aligned buffers, probe started once); runs in sections 4-6 have no crash.
