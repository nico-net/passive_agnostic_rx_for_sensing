## 1. CPU channelizer (`radio/COMMON/iq_ddc.c`)

Profile first (`mix_split` vs `stage_run` in a harness on core 16): the mixer was 0.24 ns/input sample, the halfband stages 1.5-2.0 ns. The stages were slow because the 32-byte GCC vector type (`vector_size(32)`) spills on NEON.

Changes:
- 16-byte vectors (8 accumulators of 4) in the halfband inner loop: stages 2.0 -> 0.59 ns/input sample.
- Mixer fused with the stage-0 deinterleave: the mixed samples are written straight into the even/odd phase arrays (`rot4`, a parity-split copy of the phasor table); no float scratch round trip (24 B/sample) and no deinterleave pass.
- Decim 1 (mixer only): mixer into small split buffers, then NEON `vcvtnq_s32_f32` + `vqmovn_s32` + `vst4` for round-to-nearest-even, saturate, re-interleave (same clip counter). Decim >= 2 final conversion likewise (`vst2`).

Numerics `[OFFLINE VERIFIED]`: `test_iq_ddc_equiv` compares against a frozen copy of the previous implementation (`tests/iq_ddc_ref.c`): decim 1/2/4/8 x shifts (0, -19.81 MHz, 7.3 MHz, 3.6 GHz) x block sizes not multiples of 4096, state across blocks, a reset, clipping inputs. Result: max difference 0 LSB, 0 differing samples, identical clip counts (the output is bit-exact). `test_shm_iq`, `test_shm_iq_chan`, `shm_iq_chan --selftest` pass.

`[MEASURED, DGX GB10, shm_iq_chan --bench, 1 thread on core 16, 4 channels, 1 cell, 3 reps, quiet host]`, x real time:

| ring rate / cell rate (decim) | before | after |
|---|---|---|
| 122.88 / 122.88 MS/s (1, mixer only) | 1.75 | 4.49 |
| 122.88 / 61.44 (2) | 0.89-1.09 | 2.97 |
| 122.88 / 30.72 (4) | 0.78 | 2.40 |

The review's 0.71x / 0.30x were measured on a loaded host; on core 16 the baseline is 1.75x / 0.94x, and the speed-up is the number to read. In the replay (c3610, 2 cells, CPU channelizer, 2 threads): channelizer CPU 32.5 -> 18.6 s, proc 1.02 -> 0.56 ms per 0.5 ms block (still 1.12 ms per ms: two threads cannot carry 2 cells at 1x; use the GPU backend). The decim-4 cell that decimates inside its own read thread (fan arm, no channelizer): cell B CPU 31.0 -> 23.2 s.

## 2. GPU channelizer (`shm_iq_chan_gpu.cu`, `shm_iq_chan.c`)

Where the time went `[CODE-READ + MEASURED]`: two host copies per block (ring -> staging -> pinned) and one on the way out, a synchronous call per block, mixer output and every stage's input in device memory (the GB10 LPDDR is the limit), and a 65536-sample block (0.27 ms at 245.76) that waits for a GPU slot on every submission.

Changes (ABI 1 -> 2, the v1 blocking `chan_gpu_run` stays for the selftest):
- Pinned, pre-faulted input and output slots, two slots (double buffering): `shm_iq_ring_copy` reads straight into the pinned input, the cell rings are written straight from the pinned output (no staging copies). Block k+1 is read while block k is on the GPU; the loop drains the pipeline before a retune, a discontinuity, an idle poll and at exit.
- Fused mixer + first halfband stage (`k_mix_stage0`, shared-memory tile) and fused mixer + output for decim 1: the mixed float samples never touch device memory. Same expressions in the same order, bit-identical to the unfused kernels (`ISAC_SHM_IQ_CHAN_GPU_FUSE=0` selects the old kernels; GPU-vs-CPU selftest: max 1 LSB, 129/786432 differ, identical in both modes).
- Default GPU block 1 048 576 samples (clamped to an eighth of the ring; `--block` still forces it): fewer submissions per second, each of which may wait out another context's time slice. Latency 4.3 ms at 245.76 MS/s, irrelevant against a 0.5-1 s ring.
- Stream created with the greatest priority.
- Batching over channels was already there (grid.y); it stays.

SM partition / green context: not used, on purpose `[CODE-READ + MEASURED]`. The channelizer is its own process, hence its own CUDA context. Between processes without MPS the driver time-slices whole contexts, whatever SMs a green context owns; a green context only separates streams inside one process. This matches the measured "7x slower under 2 live receivers" of the review and is why ULLDPC's second split (rc 915) cannot help here either. What does help is less GPU time per block and fewer, larger submissions (above). MPS would give true spatial sharing but changes every cell's GPU behaviour; left as an explicit decision (section 10).

## 3. Ring default 2^27

`pub_default_capacity(channels, MemAvailable, keep_free)` (`shm_iq_uhd_core.c`): 2^27 samples (2.1 GB for 4 channels; 1.09 s at 122.88, 0.55 s at 245.76 MS/s), halved while the ring would take more than half of what is free above 16 GB, never below 2^23. `shm_iq_uhd_pub` uses it when `--capacity` is not given and logs the result in `SHMIQ_UHD_READY`; `ota_mpci.sh` no longer passes its 2^25 default (`CAPACITY=` still overrides). RAM: 2.1 GB of /dev/shm per 4-channel ring (counted in the planner, section 5). Unit test `test_default_capacity` `[OFFLINE VERIFIED]`.

## 4. Multi-streamer count mismatch (`pub_mc_*`)

Before: any difference of count or tick between channels was MISMATCH, which restarted all streamers (seen on air with `--chunk 65536`: 57252 vs 59240 samples, then a cascade of DPDK drops and an abort).
Now (`pub_mc_finish`): if every channel delivered and the effective start ticks agree, the chunk is published at the shortest count; the excess of the longer channels is copied into a per-channel carry and opens the next chunk (`pub_mc_reserve` copies it into the slot and returns the slot pointer advanced by the carry; the streamer thread asks `pub_mc_want(c, n)` samples; `res[c].tick` is the tick of the newly received samples). A difference above a quarter of the chunk, a tick difference, an overflow, an error or a timeout is still MISMATCH/OVERFLOW/OTHER/IDLE and drops the carry (the caller re-arms: the ticks jump). When the carry would not fit before the ring end, the chunk is received into staging and published by `shm_iq_ring_write` (no wrap in place). New counters `shortened`, `staged` in the stats; `SHMIQ_UHD_STATS` / `SHMIQ_UHD_END` print `shortened`.
Test `test_multi_carry` `[OFFLINE VERIFIED]`: 60 chunks with alternating shorter channel through several ring wraps: no gap, no resync, both channels hold identical sample numbers, `staged > 0` exercised, a 400-sample difference (> chunk/4) is still a MISMATCH and a re-armed run continues. Not exercised with real UHD packets (OTA test, section 6).

## 5. `mpci_auto.py`

- **RAM** (`cell_ram_gb`, `ram_limit`): host + GPU memory of a receiver on the GB10's single pool, 1.1 x (13.0 + 11.0 GB at 217 PRB, 3.6 + 9.0 GB at 51 PRB, linear in PRB between and beyond: 106..189 and 273 are interpolated, not measured), plus the publisher ring and 0.2 GB for the channelizer. Cells are admitted cheapest-first while `MemAvailable - fixed - sum(costs) >= floor`; the floor is 16 GB and `--ram-floor-gb` can only raise it. Dropped cells go to `unserved` with `reason: ram`; if not even one fits the plan refuses. `--mem-avail-gb` plans for a given free RAM, `--no-ram-check` disables it. Check against the 2026-10-15 air numbers: 2 x 217 + ring = 54.9 GB estimated vs 55 GB measured drop; 508 + 249 = 42 GB vs 40 GB.
- **Core pins** (`T26F_MAP`, `apply_core_map`, launcher pseudo-key `SCAN_CORE`): the review's section 4 split. N = 2: cell A mask 0,2,3,5,6,7,12 (PDSCH 7+3, scan 5, DM-RS 2, UL 0), cell B mask 1,4,8,9,11,13,14 (PDSCH 4+11, scan 8, DM-RS 13, UL 1), channelizer core 10, publisher 15-19. N = 1 uses the whole t26f map; N = 3 adds a light cell on shared little cores (flagged `core_note`); more than 3 cells are left unserved (`reason: cores`). Pins go to the cell as `ISAC_PDSCH_CORES`, `ISAC_DMRS_SCAN_CORE`, `ISAC_PUSCH_CORES`, `ISAC_UL_SNAP_CORE` and `SCAN_CORE`, which `mpci_launch.sh` writes into that cell's cfg copy (`pdcch_blind_monitor_scan_thread`; before, the field was shared by all cells). `--core-map auto` (default) applies the map when `--cores` contains its cores, otherwise the old even split stays; `t26f` demands it, `none` disables it. USS/NID/GPU worker stay unpinned inside the mask (as in `ota_mpci.sh`).
- **Ring rate by measured capacity** (`CHAN_CAP_GPU`, `CHAN_CAP_CPU_1T`, `choose_rate`): without `--rate`, a wideband plan takes the widest window (245.76 then 122.88 MS/s) whose measured channelizer capacity for the cells it serves is >= 3.0x real time (the old 2-cell 245.76 channelizer measured 2.15x idle and ran at 0.85x on air: margin 3). With the numbers of section 2: the frontlive_data/cells.json set (4 cells fit the 245.76 window: 2.56x) is planned at 122.88 MS/s with 2 cells; 2 cells at 245.76 (4.37x) are admitted. `--rate` overrides; `radio.rate_choice` in plan.json records capacity and cell count per candidate; `--chan-table` data can be passed to `make_plan` after a new measurement.

Tests `[OFFLINE VERIFIED]` (`test_mpci_auto`, `test_mpci_launch`, 35 tests): RAM floor and cheapest-first admission (incl. a floor argument below 16 being raised), plan trimmed by RAM, exact t26f pins for 2 cells, even-split fallback, `--core-map t26f` refusal, 3-cell limit and chan-core overlap refusal, capacity-driven rate (both directions, custom table), launcher `SCAN_CORE` rewrite in the cfg copy. The two existing CLI tests that assumed a 245.76 default now state the rate or the new capacity-driven result.

## 7. Radio lines for shm cells

`shm_iq_uhd_pub` writes `/dev/shm/<ring>.radio` (capped at 64 KiB, rotation keeps the header lines; removed at close): `RFRING ch<i> port gain freq_hz rate bw_hz` per channel at start (gain and bandwidth read back from the radio), `SENSING: CHPOW sample=N dBFS ch0=..` every `--chpow-s` (default 5 s, 0 = off; the same format as usrp_lib, from the last 8192 published samples, after rx shift), and `SENSING: RFSTALL SHM_PUB reason=overflow|count_or_tick_mismatch|no_samples_100ms|stream_error ...` at every non-OK chunk. `libshm_iq.so` polls the file about once per second in the read path (also while it waits for a stalled publisher) and prints the lines to the cell's stderr, with RFRING rewritten as that cell's `RFCHAN` line (cell tuning and rate, `ring_freq=` appended). A late cell catches up on the history at once. Flags-off nothing changes (the file does not exist without the publisher).

## 10. Risks and decisions left

- The GPU channelizer gain is measured idle and under a loaded replay (same direction: 0 overruns), but the on-air 245.76 MS/s case is only predicted.
- Time slicing between the channelizer and the cell processes is not removed. MPS (true SM sharing, `CUDA_ACTIVE_THREAD_PERCENTAGE`) would, but it changes every receiver's GPU scheduling and the nomps setup used by all agents: your decision.
- Publisher carry logic is unit-tested only (real UHD packet sizes may expose new count patterns); the existing restart path is kept for everything beyond a quarter chunk.
- The side channel adds one `open/pread/close` per second to the cell's read path (negligible, not measured separately) and exists only with the standalone publisher.
- RAM estimates for 106..189 and 273 PRB are interpolated; the 1.1 margin is a fit to two air observations.
- t26f map: tied to the DGX GB10 core layout (documented in the code); `--core-map none` for other hosts. N = 3 shares little cores.
- The CPU channelizer is better but still not 1x for 2 cells on 2 threads; the planner only admits a CPU channelizer where the table says >= 3x (one cell per thread at 122.88 is 2.4x: it will fall back to 122.88 and, in practice, the GPU backend remains the default).
- Not done: zero-copy device-resident ring reads (the ring is read with one pinned copy per block; on the GB10 the remaining GPU time is kernel, not copy), the O6 arbiter back-off, O10 timed tune.
- `test_shm_iq_chan_gpu` needs the GPU and `CUDA_MPS_*` set on shared hosts.
